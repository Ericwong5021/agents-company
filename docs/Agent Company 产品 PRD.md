# Agent Company 产品 PRD

## 1. 产品概述

### 1.1 产品名称

**Agent Company**

### 1.2 一句话定位

Agent Company 是一间由 AI Agent 组成的可治理虚拟公司，用户通过对话、会议、任务和审批来驱动这家公司完成真实工作。

### 1.3 产品愿景

未来的 AI 产品不应只是“一个更聪明的聊天框”，而应该是一组可分工、可协作、可观察、可纠偏、可沉淀经验的数字员工组织。

Agent Company 的目标是让用户拥有一间自己的 AI 公司：

- 有不同角色的 Agent；
- 有组织结构、职责边界和上下级关系；
- 有会议、讨论、任务、交付和审批；
- 有工作记录、经验沉淀和声誉变化；
- 有可观察的状态，而不是黑盒式等待；
- 有治理能力，而不是失控的自动化。

用户不是“使用一个 AI 工具”，而是“经营一家公司”。

---

## 2. 核心产品理念

### 2.1 Agent 不是机器人，而是数字员工

每个 Agent 都应该被设计成一个具有持续身份的工作者，而不是一次性的模型调用。

一个 Agent 至少包含：

- 名字；
- 头像；
- 职责；
- 所属组织；
- 能力边界；
- 当前状态；
- 工作历史；
- 个人记忆；
- 与其他 Agent 的关系；
- 可使用的工具；
- 过往表现形成的声誉。

用户看到 Agent 时，应该自然理解为：

> “这是我的某位同事，他现在在做什么、擅长什么、能不能接活、最近表现如何。”

而不是：

> “这是一个 prompt 模板。”

### 2.2 公司不是聊天群，而是有组织的协作系统

群聊只是入口，不是产品本质。

Agent Company 的真实对象是一套组织协作结构：

```text
用户
  ↓
董事会 / 负责人
  ↓
部门
  ↓
项目组
  ↓
执行者
  ↓
工具与工作流
```

需求不是直接丢给一个 Agent 完成，而是在组织中流动：

1. 用户提出目标；
2. 上层 Agent 理解和澄清；
3. 需求被拆解；
4. 合适的 Agent 或团队被委派；
5. 底层执行者调用工具完成产出；
6. 结果向上汇报；
7. 上级准入；
8. 用户最终审批。

产品要让用户感觉到“组织在运转”，而不是“多个模型轮流输出”。

### 2.3 默认异步，关键节点同步

用户不应该一直盯着 AI 干活。

产品的节奏应该像真实公司：

- 会议和讨论是同步的；
- 任务执行是异步的；
- 关键决策需要用户介入；
- 普通进展通过状态、摘要和通知呈现；
- 出问题时才升级到用户。

用户的理想体验是：

> “我把事情说清楚，公司自己推进。需要我判断的时候，它来找我。”

### 2.4 可观察比自动化更重要

多 Agent 自动化最大的风险不是“做得慢”，而是“用户不知道它们在干什么”。

所以产品必须始终回答：

- 谁在工作？
- 在做什么？
- 为什么做这件事？
- 下一步是谁？
- 当前卡在哪里？
- 有没有风险？
- 我能在哪里介入？
- 最终产出是什么？
- 谁审核过？
- 为什么通过或拒绝？

任何自动化能力都必须配套可观察性。否则不是产品能力，而是黑盒风险。

### 2.5 治理优先于效率

Agent Company 不追求“让 AI 自己乱跑得最快”，而追求“在用户可理解、可控制、可追责的范围内提高产出”。

因此产品需要：

- 审批；
- 暂停；
- 停止；
- 继续；
- 重试；
- 升级；
- 复盘；
- 声誉；
- 权限；
- 组织规则；
- 上下文可见性边界。

真正的高级感不是按钮多，而是用户始终知道自己还能控制什么。

## 3. 目标用户

### 3.1 核心用户

#### 个人开发者 / 独立创造者

他们希望拥有一个小型 AI 团队，帮助自己完成：

- 编码；
- 调研；
- 产品设计；
- 文档写作；
- Bug 修复；
- PR 审查；
- 方案评估；
- 自动化任务。

他们通常没有真实团队，但有真实项目。

Agent Company 对他们的价值是：

> “我一个人，也可以像带着一个小团队一样工作。”

#### 产品 / 工程负责人

他们关心：

- 多角色视角；
- 方案讨论；
- 任务拆解；
- 风险识别；
- 执行跟踪；
- 产出审批。

Agent Company 对他们的价值是：

> “我可以让 AI 团队先讨论、拆解和执行，我只在关键处拍板。”

#### 高阶 AI 工具用户

他们已经不满足于单 Agent 聊天，开始遇到：

- 上下文混乱；
- 多任务失控；
- 不知道哪个 Agent 负责什么；
- 自动化执行不可追踪；
- 产出质量不稳定；
- 缺少长期记忆和组织沉淀。

Agent Company 对他们的价值是：

> “把松散的 AI 能力组织化。”

## 4. 产品中的核心对象

## 4.1 Workspace：公司空间

Workspace 是用户拥有的一间 Agent 公司。

它不是普通项目空间，而是包含组织、任务、会议、产出、规则和历史的完整工作环境。

### Workspace 包含

- 公司名称；
- 当前目标；
- 组织结构；
- Agent 列表；
- 群组 / 会议；
- 任务看板；
- 文档和产物；
- 决策记录；
- 审批记录；
- 公司规则；
- 运行状态；
- 活动流。

### Workspace 首页需要回答

用户进入产品第一眼应该知道：

- 当前公司是否正常运转；
- 有多少 Agent 在线；
- 有多少任务进行中；
- 哪些事情等待用户审批；
- 最近有什么重要进展；
- 哪些 Agent 正在工作；
- 哪些任务有风险；
- 下一步建议用户做什么。

---

## 4.2 Agent：数字员工

Agent 是产品的核心人格单元。

### Agent 基础字段

- 名称；
- 头像；
- 角色；
- 职责描述；
- 所属部门 / 团队；
- 当前状态；
- 当前任务；
- 可用工具；
- 模型配置；
- 工作偏好；
- 记忆；
- 声誉；
- 最近活动；
- 权限等级。

### Agent 状态

Agent 状态必须精细，不应只有 busy / idle。

建议状态：

| 状态 | 含义 |
|---|---|
| `idle` | 空闲，可接收任务 |
| `thinking` | 正在理解、规划或等待模型响应 |
| `working` | 正在执行任务 |
| `speaking` | 正在群聊中发言 |
| `queued` | 已排队，等待发言或执行 |
| `waiting_approval` | 等待用户或上级审批 |
| `blocked` | 被问题阻塞，需要处理 |
| `reviewing` | 正在审查他人产出 |
| `done` | 最近任务完成 |
| `error` | 最近执行失败 |
| `muted` | 当前会议或任务中被静音 |
| `offline` | 不可用 |

### Agent 详情页

Agent 详情页应该像一个员工档案。

必须包含：

- 角色说明；
- 当前职责；
- 所属组织；
- 当前工作；
- 工作历史；
- 最近产出；
- 声誉变化；
- 常用技能；
- 可用工具；
- 记忆摘要；
- 指令编辑；
- 与其他 Agent 的协作关系。

用户在这里可以完成：

- 修改职责；
- 调整工作偏好；
- 查看表现；
- 指派任务；
- 暂停或恢复；
- 查看上下文；
- 查看历史贡献。

---

## 4.3 Group / Meeting：协作房间

Group 是多个 Agent 和用户共同讨论的空间。

它不是普通微信群，也不是单纯任务流。它的本质是“可治理会议”。

### 群聊页面必须回答

- 当前群组是谁？
- 有哪些成员？
- 当前发言策略是什么？
- 谁正在说话？
- 谁正在思考？
- 谁排队发言？
- 当前第几轮？
- 用户是否可以暂停、继续、跳过或点名？
- 本轮讨论的目标是什么？
- 最后形成了什么决定？

### 消息时间线

群聊消息必须逐条呈现，不应把多个 Agent 输出合并成一个大块。

每条消息必须清楚展示：

- 发言者；
- 角色；
- 发言时间；
- 消息内容；
- 是否是思考、建议、决定、工具结果或系统事件；
- 是否与某个任务、文件或决策相关。

用户消息靠右，Agent 消息靠左。Supervisor 或主持人只有在真正主持、总结、调度时才突出显示，不应把所有 Agent 回复都包装成 supervisor 结果。

### 发言策略

群聊必须支持不同讨论模式。

| 模式 | 使用场景 |
|---|---|
| 自动模式 | 系统判断谁应该发言 |
| 轮流模式 | 所有成员按顺序回应 |
| 点名模式 | 只有指定成员回应 |
| 手动模式 | 用户选择下一位发言者 |
| 静默模式 | 只记录用户消息，不自动触发 Agent |

### 群聊控制

用户应能在会议中执行：

- 暂停本轮；
- 继续本轮；
- 停止本轮；
- 跳过某位 Agent；
- 点名某位 Agent；
- 静音某位 Agent；
- 让所有成员回应；
- 增加一轮；
- 结束并总结；
- 从讨论生成任务；
- 从讨论生成决策；
- 从讨论生成文档。

---

## 4.4 Task / Issue：工作单元

Task 是 Agent Company 中最重要的执行对象。

任务不是一句 prompt，而是一份可追踪、可验收的工作单。

### Task 字段

- 标题；
- 描述；
- 发起人；
- 负责人；
- 参与 Agent；
- 所属项目；
- 状态；
- 优先级；
- 工作类型；
- 验收标准；
- 当前阶段；
- 产出物；
- 审批记录；
- 事件日志；
- 风险；
- 截止时间；
- 关联讨论；
- 关联决策。

### Task 状态

| 状态 | 含义 |
|---|---|
| `draft` | 草稿 |
| `queued` | 已排队 |
| `planning` | 正在拆解 |
| `assigned` | 已分派 |
| `running` | 正在执行 |
| `reviewing` | 正在审查 |
| `waiting_approval` | 等待审批 |
| `blocked` | 阻塞 |
| `completed` | 完成 |
| `failed` | 失败 |
| `cancelled` | 已取消 |
| `archived` | 已归档 |

### Task 详情页

任务详情页应包含：

- 任务目标；
- 验收标准；
- 当前负责人；
- 当前状态；
- 进度时间线；
- Agent 活动日志；
- 关键产出；
- 审查意见；
- 阻塞原因；
- 用户可执行动作。

用户可以：

- 审批；
- 拒绝；
- 要求修改；
- 暂停；
- 取消；
- 重新分派；
- 升级给上级 Agent；
- 查看产出；
- 查看执行日志；
- 生成复盘。

## 4.5 Artifact：产出物

Artifact 是 Agent 工作的结果。

可以是：

- 代码 diff；
- PR；
- 文档；
- 调研报告；
- 设计稿；
- 表格；
- 分析结果；
- 决策建议；
- 会议纪要；
- 测试结果；
- 计划书。

Artifact 不是聊天附件，而是公司资产。

### Artifact 需要展示

- 标题；
- 类型；
- 生成者；
- 所属任务；
- 当前版本；
- 创建时间；
- 更新时间；
- 摘要；
- 内容预览；
- 审批状态；
- 关联讨论；
- 关联决策；
- 下载 / 打开 / 复制入口。

### Artifact 状态

| 状态 | 含义 |
|---|---|
| `draft` | 草稿 |
| `submitted` | 已提交 |
| `reviewing` | 审查中 |
| `approved` | 已批准 |
| `rejected` | 已拒绝 |
| `superseded` | 已被新版本替代 |
| `archived` | 已归档 |

---

## 4.6 Decision：决策

Agent Company 必须保存重要决策。否则组织无法学习。

### Decision 来源

- 用户拍板；
- 董事会会议；
- 任务准入；
- 方案选择；
- 风险处置；
- 组织变更；
- 审批结果。

### Decision 字段

- 决策标题；
- 决策内容；
- 决策人；
- 参与讨论者；
- 备选方案；
- 最终选择；
- 理由；
- 反对意见；
- 生效范围；
- 关联任务；
- 关联产物；
- 创建时间。

用户应该能够回看：

> “当时为什么这么决定？”

---

## 4.7 Proposal：提案

Proposal 是组织自下而上的主动能力。

Agent 不只是被动接活，也可以提出建议。

### Proposal 场景

- 某 Agent 发现流程可以优化；
- 某 Agent 发现项目风险；
- 某 Agent 建议引入新工具；
- 某 Agent 发现组织缺少某种角色；
- 某 Agent 建议重构某个模块；
- 某 Agent 根据外部变化提出行动建议。

### Proposal 状态

| 状态 | 含义 |
|---|---|
| `created` | 已提出 |
| `discussing` | 讨论中 |
| `accepted` | 已采纳 |
| `rejected` | 已否决 |
| `deferred` | 延后 |
| `converted_to_task` | 已转任务 |

用户体验上，提案应该像公司内部建议，而不是系统弹窗。

## 5. 核心用户旅程

## 5.1 第一次进入

用户第一次进入产品时，不应该看到空白系统，而应该看到一间待启动的公司。

### 首屏目标

让用户理解三件事：

1. 这是你的 AI 公司；
2. 你可以通过对话驱动它；
3. 它会把工作拆给不同 Agent 执行，并在关键处请求你审批。

### 首次引导

建议流程：

1. 创建 Workspace；
2. 选择公司目标；
3. 初始化几个基础 Agent；
4. 进入圆桌会议；
5. 用户描述第一个目标；
6. Agent 帮用户澄清；
7. 系统生成第一个任务；
8. 用户确认；
9. Agent 开始执行；
10. 首页出现真实活动。

### 默认 Agent 示例

- CEO / Coordinator：理解用户目标，组织讨论；
- Product Lead：拆需求，定义验收；
- Engineer：执行编码任务；
- Reviewer：审查产出；
- Researcher：调研和事实核查。

---

## 5.2 发起一个需求

用户可以用自然语言说：

> “帮我把这个项目里的群聊体验设计清楚，并拆出任务。”

系统不应该立刻执行，而应该进入“理解和组织”流程。

### 理想流程

1. 用户提出需求；
2. 负责人 Agent 复述目标；
3. 如果信息不足，提出澄清问题；
4. 如果目标清楚，召集相关 Agent；
5. 多 Agent 讨论方案；
6. 形成任务拆解；
7. 用户确认；
8. 分派执行；
9. 执行过程中展示状态；
10. 完成后提交产物；
11. 用户审批或要求修改。

---

## 5.3 多 Agent 群聊讨论

### 讨论过程

用户进入群聊后，可以选择：

- 只和主持 Agent 聊；
- 点名一个 Agent；
- 让所有 Agent 依次回应；
- 让系统自动选择合适的人发言。

### 多 Agent 发言要求

每个 Agent 的发言都必须有明确身份。

错误体验：

> “团队认为：…… ”

正确体验：

```text
Product Lead：
我认为这里需要先定义主用户路径。

Engineer：
从实现角度看，状态模型需要先稳定。

Reviewer：
我建议在进入开发前明确验收标准，否则后续会反复。
```

### 用户控制

用户可以随时：

- 打断；
- 暂停；
- 纠偏；
- 要求总结；
- 要求转任务；
- 要求某人单独回答；
- 结束讨论。

---

## 5.4 任务执行与观察

任务执行时，用户不需要一直看日志，但必须能随时进入查看。

### 执行中页面应展示

- 当前负责人；
- 当前步骤；
- 最近动作；
- 是否卡住；
- 当前产出草稿；
- 预计下一步；
- 是否需要用户介入。

### 活动流示例

```text
10:12 Product Lead 创建任务说明
10:13 Engineer 认领任务
10:14 Engineer 读取相关文件
10:17 Engineer 修改实现
10:21 Reviewer 开始审查
10:24 Reviewer 提出 2 条修改意见
10:29 Engineer 完成修复
10:31 Reviewer 通过
10:32 等待用户审批
```

---

## 5.5 审批与准入

审批是产品中非常关键的信任机制。

### 审批出现的场景

- 执行前确认；
- 重要方案选择；
- 文件写入；
- 代码提交；
- PR 合并；
- 组织变更；
- 生产环境操作；
- 高成本任务；
- 权限提升；
- 提案采纳。

### 审批卡片必须包含

- 谁请求审批；
- 要做什么；
- 为什么要做；
- 影响范围；
- 风险；
- 可选项；
- 推荐动作；
- 拒绝后会怎样；
- 批准后会怎样。

### 用户动作

- 批准；
- 拒绝；
- 要求修改；
- 查看详情；
- 委托某 Agent 判断；
- 永久信任类似操作。

---

## 5.6 失败与升级

Agent 失败不应该只是显示 error。

失败要成为组织过程的一部分。

### 失败时必须说明

- 哪个 Agent 失败；
- 在哪个任务阶段失败；
- 尝试了什么；
- 失败原因是什么；
- 是否可恢复；
- 下一步建议是什么；
- 是否需要升级给上级；
- 用户能做什么。

### 失败后的动作

- 重试；
- 换方案；
- 换 Agent；
- 降低目标；
- 请求更多上下文；
- 升级给负责人；
- 标记为失败并复盘。

## 9. 声誉与学习

### 9.1 声誉的作用

声誉不是给 Agent “打鸡血”，而是帮助组织更好地分配工作。

声誉影响：

- 任务路由；
- 重要任务负责人选择；
- 审查强度；
- 提案权重；
- 是否晋升；
- 是否需要再训练；
- 是否适合继续承担当前职责。

### 9.2 声誉来源

- 任务是否完成；
- 审查是否通过；
- 修改轮数；
- 是否超预算；
- 是否造成失败；
- 用户评价；
- 上级 Agent 评价；
- 是否提出有价值提案；
- 是否错误批准了低质量产出。

### 9.3 学习沉淀

每次任务结束后，系统应能沉淀：

- 这类任务怎么做更好；
- 哪些上下文有用；
- 哪些错误重复出现；
- 哪个 Agent 更适合；
- 是否应形成 skill；
- 是否应修改组织规则。

## 10. 权限与上下文

### 10.1 为什么需要权限

多 Agent 系统如果没有上下文边界，很快会变成所有 Agent 共享所有信息，既浪费 token，也不符合组织感。

### 10.2 可见性原则

每个 Agent 只能看到：

- 与自己职责相关的信息；
- 所属团队共享信息；
- 公司公共信息；
- 被授权查看的任务；
- 必要的历史记忆。

### 10.3 信息分层

- 公司公开信息；
- 团队共享信息；
- 项目私有信息；
- Agent 私人记忆；
- 受限敏感信息。

用户体验上，不需要暴露复杂权限系统，但需要让用户知道：

> “这个 Agent 为什么知道这些、不知道那些。”

## 11. 空状态、加载状态与错误状态

### 11.1 空 Workspace

应引导用户：

- 创建第一个目标；
- 进入圆桌；
- 选择默认 Agent；
- 发送第一条需求。

### 11.2 空群聊

应提示：

- 可以发起讨论；
- 可以点名成员；
- 可以让全员回应；
- 可以从讨论生成任务。

### 11.3 空任务

应提示：

- 从输入框创建任务；
- 从会议生成任务；
- 从提案转任务；
- 查看示例任务。

### 11.4 Agent 失败

错误信息必须具体：

错误体验：

> “执行失败。”

正确体验：

> “Engineer 在修改文件时失败，因为目标文件不存在。可以让它重新扫描项目结构，或把任务升级给 Tech Lead 重新拆解。”

## 12. 产品气质

### 12.1 视觉气质

Agent Company 应该是：

- 专业；
- 克制；
- 高密度；
- 可扫描；
- 有状态感；
- 有组织感；
- 有轻微未来感；
- 不娱乐化；
- 不像游戏玩具；
- 不像普通后台模板。

### 12.2 文案气质

文案应该像一个可靠的公司助理，而不是营销机器人。

避免：

- 夸张；
- 卖萌；
- 空泛鼓励；
- “魔法式”表达；
- 过度拟人到不可信。

推荐：

- 清楚；
- 具体；
- 有上下文；
- 告诉用户下一步；
- 说明影响和风险。

### 12.3 交互气质

用户应该感到：

- 系统在主动推进；
- 但不会越权；
- 信息很多但不混乱；
- Agent 有身份但不过度表演；
- 自动化强但可暂停；
- 出问题时能解释；
- 做完的东西能追溯。

---

## 13. 成功标准

### 13.1 用户感知成功

用户使用后应该能说：

- “我知道每个 Agent 在做什么。”
- “我可以让多个 Agent 一起讨论。”
- “我可以放心让它们先执行。”
- “关键操作会来找我确认。”
- “失败时我知道怎么处理。”
- “产出不是散落在聊天里，而是沉淀成资产。”
- “这更像一间公司，而不是一个聊天机器人。”

### 13.2 产品体验成功

产品应达成：

- 新用户 5 分钟内理解核心概念；
- 用户能顺利发起第一个需求；
- 多 Agent 群聊身份清晰；
- 任务状态可追踪；
- 审批动作明确；
- 产物可回看；
- 失败可恢复；
- 首页可一眼看出公司状态。

---

## 14. 总结

Agent Company 的产品核心不是“做一个多 Agent 聊天界面”，而是设计一套 **AI 组织操作系统**。

它有三个最重要的产品判断：

1. **Agent 必须有持续身份**，否则只是 prompt；
2. **协作必须有组织结构**，否则只是群聊；
3. **自动化必须可治理**，否则用户不会信任。

最终，这个产品应该让用户感觉：

> 我不是在操作一堆 AI 工具。  
> 我是在经营一间由 AI 员工组成的公司。
