# 01. 组织架构设计

> **模块**：组织架构
> **核心问题**：谁在哪、干什么、怎么管
> **来源**：运转模型宪法 §1

---

## 1. 固定层级结构

组织是一棵**固定层级的递归委托树**，不可越级：

```
用户 ←→ 董事会圆桌（CEO/CTO/CFO/CMO）   ← 系统入口 = 一场会议
        │ 高认知 + 业务前沿 → 定方向、定优先级
        ↓
     部门层
       ├── 业务部门（CTO/CMO/CFO 各自的部门）← 拆目标 + 定验收标准 + 组团队
       └── 基建部门（Infrastructure）← 跨部门协作案例库 + 可复用工作流 + 共享 Agent
        ↓
     项目组（Leader）         ← 拆解为可执行规格 + 招募成员 + 管准入
        ↓
     执行层                   ← 按协作流程编排交付：匹配预定义工作流 + 细化规格 + 驱动工具
        ↓
     工具层                   ← 唯一直接产出制品的层
       编码 / 检索 / 写作 / 设计 / 分析 …
```

### 关键规则

- **严格不可越级**：每层必须经过，不设跳步——跳步让 Agent 行为路径发散，难以规范
- **统一递归角色**：每个非叶节点 = {拆解目标, 招募/委派, 准入校验, 失败升级}
- **拆解 = 层间向下委派**，不是单个 Agent 任务内部的阶段
- **委派深度 ≈ 4-5 层**

## 1.5 董事会运行模式

董事会存在两种运行模式，由用户决定切换时机：

### 阶段一：User-led（用户主导）

```
董事会圆桌 = [用户(Leader) + CEO(AI) + CTO(AI) + CFO(AI) + CMO(AI)]
```

| 行为 | 定义 |
|------|------|
| 发起会议 | 用户发起，AI 董事响应 |
| 主持讨论 | 用户主持 |
| 发言权重 | 用户 = 最高 |
| 最终拍板 | 用户拍板，CEO 无最终否决权 |
| DRI 分配 | 各域 DRI 归各董事，但用户对所有域有 override |

### 阶段二：CEO-led（CEO 主导）

```
董事会圆桌 = [CEO(Leader) + CTO(AI) + CFO(AI) + CMO(AI) + 用户(Participant)]
```

| 行为 | 定义 |
|------|------|
| 发起会议 | CEO 发起，按节奏自动开 |
| 主持讨论 | CEO 主持 |
| 发言权重 | 用户 = 普通参与者（可发言、可提异议，但不主持） |
| 最终拍板 | CEO 拍板 |
| 用户提异议 | CEO 必须认真回应，但决定权仍在 CEO |
| 用户越权拍板 | 系统提醒"当前 leader 是 CEO" |

### 放权与召回

- **放权**：用户主动发起，一次性放权，需明确确认（展示权限变更摘要）
- **放权时约定**：用户与 CEO 约定召回条件和回收流程
- **用户主动召回**：任何时候都可以收回领导权，即时生效，CEO 降级为普通董事
- **约定条件触发**：放权时约定的条件达成 → 系统通知用户，用户确认后召回
- **召回不是自动弹劾**：最终决定权始终在用户手里

### 放权后用户保留的权限

即使在阶段二，用户始终保留：

| 保留权限 | 原因 |
|----------|------|
| 战略方向设定 | 用户是组织的终极 owner |
| 重大事项召回 | 超预算、方向偏离、安全红线 → 系统拉用户回来 |
| 随时收回领导权 | 不可剥夺 |
| 查看任何信息 | 用户不受 scope/clearance 限制 |

## 2. 任务评级

每个任务带**评级**，决定**入口**不同，但**链路相同**——严格不可越级，每层只做自己的事：

| 评级 | 入口 | 链路 |
|------|------|------|
| 公司级 | 董事会圆桌讨论 | 董事会 → 部门 → 项目组 → 执行层 → 工具层 |
| 项目级 | 董事会成员直接指派给对口部门 | 部门 → 项目组 → 执行层 → 工具层 |
| 个人级 | 部门经理判断是否需要组建项目组 | 项目组 → 执行层 → 工具层 |

**严格不可越级**：无论任务大小，每层必须经过。不设跳步——跳步会让 Agent 行为路径发散，难以规范。

## 3. 各层级角色职责

### 3.1 董事会圆桌（系统入口）

- **组成**：CEO/CTO/CFO/CMO + 用户（阶段一为 Leader，阶段二为 Participant）
- **职责**：
  - 高认知 + 业务前沿 → 定方向、定优先级
  - 讨论原始需求，分配给对口部门负责人
  - 公司级决策的 DRI（直接责任人）
- **不做什么**：不直接上手干活，不微管具体任务

### 3.2 部门（负责人）

- **职责**：
  - 接收董事会需求
  - 拆目标 + 定验收标准
  - 组建项目组
  - 签批增员提案
- **不做什么**：不亲自执行，不自己产出制品

### 3.2b 基建部门（Infrastructure）

- **定位**：跨部门协作的公共基础设施提供者
- **职责**：
  - 维护跨部门协作案例库（沉淀历史协作经验）
  - 维护可复用工作流库（标准化协作流程）
  - 管理共享 Agent（代码审查、文档审查、安全审计等）
  - 编排联合交付工作流（端到端可见）
- **服务方式**：
  - 业务部门需要跨部门能力时，向基建部门申请
  - 基建部门派遣共享 Agent 或提供工作流
  - 联合交付的协作过程对所有参与方端到端可见
- **不做什么**：不做业务决策，不参与业务部门的目标拆解
- **新增机制**：当出现新的跨部门协作需求时，基建部门负责创建工作流并沉淀为可复用资产

### 3.3 项目组（Leader）

- **职责**：
  - 拆解为可执行规格
  - 招募团队成员
  - 管理准入验收
  - 可向上升级失败
- **不做什么**：不自己产出制品，不决定用什么工作流

### 3.4 执行层

- **职责**：
  - 拿到 spec → 匹配预定义工作流 → 用工具执行
  - 细化规格为工具可执行的指令
  - 驱动工具产出
  - 提交准入验收
- **约束**：
  - 必须使用预定义工作流（Claude Code、Codex 等），不允许自行摸索
  - 工作流缺失时，上报"工作条件缺失"，由管理层负责寻找或创建工作流
  - 每层最多尝试 2 种方案
- **不做什么**：不跳过验收，不自定义验收标准，不自己发明工作流

### 3.5 工具层

- **职责**：直接产出制品（代码/文档/数据/设计稿）
- **类型**：编码 CLI / 检索 / 写作 / 设计 / 分析
- **产出**：制品（artifact），经准入验收向上流转
- **不做什么**：不自行决定方向，不跳过执行层直接对接项目组

## 4. 优先级与控制面

### 4.1 战略/战术分层

- **战略层（用户在圆桌）**：定方向、压约束、怼方案
- **战术层（组织自排）**：具体执行顺序由组织自行决定

### 4.2 控制面三层

| 层 | 控制方式 |
|----|----------|
| **入口（圆桌）主动** | 定目标/约束/优先级——战略层满控制 |
| **执行中给闸** | 观测日志 + 急停 block + 纠偏（找负责人） |
| **交付（顶层准入）主动** | 重要交付由用户最终签字 |

### 4.3 信任旋钮

新用户初期多上浮审批门（自动准入阈值低），信任建立后调高自治。

### 4.4 用户纠偏通道

- 用户可观察各下级组织的执行日志
- 发现流程问题 → 找负责人沟通
- 若建议有益，负责人把规则写进所属组织的 instruct

## 5. 主动闭环：自底向上提案

### 5.1 提案 = delegate 的镜像

- 下级产出提案 → 流给上一级 → 三选一：**采纳**（转成任务）/ **搁置**（backlog）/ **否决**（归档带理由）
- 超出上级权限 → 继续向上冒，最终到董事会/用户

### 5.2 两道闸

| 闸 | 规则 |
|----|------|
| **闸一：生成 → 试验** | 权限内自助：下级可在自己权限内 + 隔离工作区做小范围试验，无需上级批 |
| **闸二：试验 → 生产** | 必须上级审批：应用到生产环境 / 影响产品方向，一律上级签字 |

**原则**：便宜可逆的探索放开，昂贵不可逆的落地设闸。

### 5.3 三个触发源

| 触发 | 形态 |
|------|------|
| **节奏（周会）** | 定期低成本 review → 冒提案 |
| **里程碑（项目到阶段）** | 进度触发前瞻 review → 优化/提效提案 |
| **环境扫描（空闲探索）** | 空闲 Agent 扫领域新技术/方法论 → 提案应用 |

### 5.4 学习闭环

环境扫描 → 提案 → 权限内试验 → 见效 → 上级批准入生产 → 结晶成 skill。组织能力自生长。

## 6. 组织变更规则

### 6.1 招募 ≠ 增员

| 概念 | 定义 |
|------|------|
| **招募** | 从现有 Agent 组队（临时 group） |
| **增员** | 出现能力缺口时新建 Agent |

### 6.2 增员流程

1. 拆解检测到 skill gap
2. 触发「招聘」提案
3. 上级签字
4. onboard：实例化文件束（soul 模板 + instruct 由招聘经理写 + 空 relationship/memory）

### 6.3 裁撤

- 长期低声誉 → 上级决定再培训/调岗/裁撤
- **裁撤 = 归档不删**：保留工作记录，可返聘

### 6.4 晋升

- 基于声誉数据 + 提案签名驱动

---

## 7. 决策规则

### 7.1 DRI（直接责任人）

- 每个决策域有**一个**问责人
- 听完输入后拍板——**不投票表决**
- 层级提供责任人：圆桌=CEO，部门内=负责人，准入=该级 reviewer

### 7.2 投票仅作咨询

- 不绑定结果
- 高声誉意见权重更高
- 责任人仍决定

### 7.3 辩论有界

- 限轮数
- 到点责任人拍板（防无限争论）

### 7.4 跨级申诉有界

- 下级可上诉一级
- 到顶即终局
- 允许真实 pushback，防抗命死循环
