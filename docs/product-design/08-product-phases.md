# 08. 产品阶段规划

> **模块**：产品阶段
> **核心问题**：先做什么、后做什么
> **来源**：产品阶段计划 + 运转模型宪法 §12

---

## 1. 两条正交的演进轴

```
产品能力阶段（Product Phases）  P0 → P1 → P2 → P3 → P4 → P5
        ↓ 框架一次定稿，后续不大改
分发与商业阶段（Release Tracks） R1 → R2 → R3 → R4
```

- **P 回答**：「这间办公室能干什么？」
- **R 回答**：「产品跑在哪、谁访问、怎么商业化？」

---

## 2. 产品能力阶段（P0-P5）

### P0 — 执行底座 ✅

- **一句话**：单任务链路真跑
- **范围**：runtime 接入、结构化活动契约、真交付、审批、取消
- **状态**：✅ 已完成
- **宪法定位**：编码工作类型的交付插件，非普适路径

### P1 — 执行模型 + 多 Agent

- **一句话**：Agent=文件束、模型=动力、并发单位=线程
- **范围**：
  - 主线 + 响应线并发
  - Presence 活动登记表
  - 状态 per-thread rollup
  - 共享文件写串行化
  - 多 Agent CRUD、工位状态
- **验收**：≥3 Agent 并发；一个 Agent 专注主任务时可并发响应同事
- **依赖**：P0

### P2 — 组织上下文底座

- **一句话**：协作的前提——上下文注入升级为组织信息架构 × 密级 × 访问者求交
- **范围**：
  - 上下文解析器（扫/过/聚/截/配）
  - 作用域 × 密级
  - clearance 从组织树推导 + relationship 边
  - 三层文件树 + front-matter
  - bootstrap
  - read_doc
  - 最小 delegate/message_agent + AgentMessage + inbox
- **验收**：不同 clearance 可见性不同、instruct 含名册摘要、delegate 按名解析
- **依赖**：P1
- **关键纠偏**：org-context **必须早于协作**——没有名册/角色/clearance，Agent 间无法有意义协作

### P3 — 交互 + 递归委派

- **一句话**：需求在组织里递归拆解—委派—准入/升级地流动
- **范围**：
  - A2A 对齐
  - delegate/message_agent/reply/propose/meeting 原语
  - 递归层级（董事会→部门→项目组→执行→工具层）
  - 任务评级 + 有界跳步
  - 失败协议（方案≤2 + 修复迭代 + 升级泄压）
  - 准入分级
  - 工作类型抽象（编码=P0；非编码适配器）
- **验收**：一条需求从圆桌端到端跑通；非编码工作类型至少一条可交付+准入
- **依赖**：P2

### P4 — 治理 + 学习

- **一句话**：组织会自我评价、自我进化、主动提案
- **范围**：
  - 声誉/荣誉分
  - 组织变更（增员/裁撤）+ DRI 决策规则
  - 主动提案闭环（周会/里程碑/环境扫描→提案→两道闸）
  - 经验→skill 结晶
  - token 全链路统计 + block 急停
  - 分层控制面 + 信任旋钮
- **验收**：下级能主动提案、经采纳转任务；声誉影响选人；项目可 block；token 全链路可见
- **依赖**：P3

### P5 — 体验与空间闭环

- **一句话**：组织/协作/声誉/信息流演出出来
- **范围**：
  - 差异化演出
  - 在场化交互
  - 办公室布局/装修/地图编辑
  - 递归层级树 + thread 连线 + 声誉可视
  - 董事会圆桌入口 UX
  - 回放夹具
  - Onboarding
- **验收**：派任务→看小人协作/请示→审批→看交付；组织结构与信息流动在办公室可读
- **依赖**：P0 活动契约 + P3/P4 事件
- **特殊**：无后端依赖项可与 P1-P4 并行

## 3. 分发阶段（R1-R4）

### R1 — Local Web 开源首发

- **形态**：localhost PWA
- **包含**：P0-P5 全部完成
- **非目标**：多租户、官方托管、桌面打包、手机 App

### R2 — 官方 Server + 多租户

- **增加**：官方 Server、OAuth/JWT、DB 持久化、SSE/WS、团队共享
- **不变**：执行模型

### R3 — PC 客户端 + 云端 Runtime

- **增加**：桌面安装包、sidecar daemon、云端 Runtime（可选）

### R4 — 手机端

- **增加**：手机管理端、Push
- **不移植**：完整办公室

## 4. 实施顺序

```
P0 ✅ 执行底座
  ↓
P1 执行模型 + 多 Agent（文件束/线程/Presence）
  ↓
P2 组织上下文底座（org-context，前移）   ← 协作的前提
  ↓
P3 交互 + 递归委派（含工作类型）
  ↓
P4 治理 + 学习（声誉/提案/决策/组织变更）
  ↓
P5 体验与空间闭环（living office）
  │
  └─→ P5 无后端依赖项可与 P1-P4 并行
  ↓
R1 首发验收（P0-P5 全集）
```

---

## 5. R1 首发验收标准

在 Local · Web · 开源形态下，用户无需官方托管即可完成：

1. **多 Agent**：创建并同时运行多个 Agent，办公室内状态可区分
2. **工作区**：每 Agent 有独立工作区与 instruct；任务策略可配置
3. **流转**：至少一条跨 Agent 编排可端到端跑通
4. **组织**：基本组织架构与 Agent 归属可配置，并反映到办公室视图
5. **空间**：办公室布局可编辑、持久化、重启后保留
6. **体验**：演出与在场化交互覆盖派任务、审批、交付主路径
7. **交付**：PR 或本地 diff 审查合并闭环；任务可取消

---

## 6. 设计原则

| 原则 | 说明 |
|------|------|
| 框架一次定稿 | P1-P3 的数据模型与 API 按可扩展设计，第一版就定语义 |
| 演出挂真数据 | P5 依赖 P0 契约；禁止假演出撑场面 |
| 不自研执行引擎 | 始终封装成熟 CLI runtime |
| 服务端是权威 | 前端不虚构执行状态 |
| org-context 前移 | 协作的前提是组织上下文 |
