# 工作类型与领域适配器

> 状态：当前
> 上位文档：[产品宪法](PRODUCT-CONSTITUTION.md)

## 1. 产品边界

Agent Company 首先是一套领域中立的 Agent 自组织与自治理系统，不是一支只会编程的固定团队，也不是把若干专家机器人摆在同一个界面里。

用户提出目标后，系统根据交付物、风险、资源、权限和验证方式动态形成团队。Agent 可以积累长期身份和专长，但本次任务中的责任、协作关系、能力包和工具由目标决定。固定的是治理协议、工作契约、权限边界和界面语法，不是永久工种阵容。

Pre-Public 不要求穷尽所有行业和外部应用，但必须证明同一套组织内核能跨越不同工作类型，不因进入软件研发、研究、写作或本地应用操作而换成另一套产品。

## 2. 通用工作契约

所有领域共享以下闭环：

```text
Goal
→ Charter
→ 动态团队与临时责任
→ Work Item + 资源 + 权限 + 能力包
→ 受管执行与失败恢复
→ 可审查制品
→ 领域验证
→ Gate / Approval / Decision
→ Delivery + 资源处置
→ Reflection / Ambient
```

通用对象包括 Project Charter、Work Item、Thread、Artifact、Agent Run、Admission、Decision、Approval 和 Audit Event。领域适配器只补充输入、工具、制品、验证器、副作用和回滚协议，不重新定义组织。

每个 Work Item 至少回答：

- 要解决什么问题，交付给谁；
- 使用哪些输入和受管资源；
- 哪些 Agent 承担什么临时责任；
- 可以调用哪些能力包、工具和外部系统；
- 怎样证明结果正确；
- 失败后如何重试、升级、回滚或保留现场；
- 完成后如何处置临时资源。

## 3. 首发代表性工作类型

首发至少用三类任务验证通用内核：

| 工作类型 | 代表性制品 | 核心验证 | 典型受管资源 |
|---|---|---|---|
| 研究与分析 | 研究报告、证据包、结论 | 来源追踪、交叉验证、时效性、假设审计 | 网页、文档、数据文件 |
| 文档与本地应用 | 文稿、表格、演示、应用内结果 | Rubric、回读验证、副作用确认、必要回滚 | 本地文件、桌面应用、用户授权数据 |
| 软件研发 | Charter、代码 diff、提交、测试与 Review | 测试、构建、独立审查、主分支验证 | Git 仓库、Worktree、构建环境 |

这三类是验收切片，不是固定部门，也不是三套预装 Agent。一次目标可以组合多类能力，例如先研究再写方案，随后修改代码并生成发布说明。

## 4. 能力包不等于员工

能力包描述可调用的工具、上下文规则、验证器和运行约束。员工 Agent 描述持续身份、经验、关系、权限历史和职业成长。两者不能混为一谈。

- 同一能力包可以被多个 Agent 使用；
- 同一 Agent 可以在不同目标中使用不同能力包；
- 动态组队先看 Charter 所需能力，再结合声誉、成本、关系和可用性选人；
- 长期岗位可以存在，但不能成为所有目标必须经过的固定流水线；
- 执行者不能在要求独立审查的 Gate 中自我批准。

界面可以清晰展示“这次由谁负责研究、谁负责验证”，但不应诱导用户先招聘一套完整专家团队才能开始工作。

## 5. 软件研发适配器

软件研发是首发中治理最深的领域适配器，不是产品的全局边界。

### 5.1 输入

- 一个或多个明确声明的软件交付单元；
- 每个交付单元优先对应一个主 Git 仓库；
- 用户目标和 Project Charter；
- 分支、Worktree 与合并策略；
- 允许的工具、网络和外部权限；
- 仓库规则、构建和测试命令。

### 5.2 临时责任

软件任务可能需要 Product DRI、Technical Lead、Engineer、Reviewer、Test、Security、Design 或 Research 等责任。它们是当前 Charter 下的责任，不等于必须长期雇佣七类专职 Agent。

低风险小任务中，同一个 Agent 可以兼任多个责任；需要独立审查时，执行者不能自我批准。

### 5.3 制品与验证

- Project Charter 与技术方案；
- 代码 diff 和提交；
- 测试、构建、类型检查、Lint 或安全报告；
- Review findings 与处理记录；
- 合并提交和主分支验证；
- 必要的文档、迁移和发布说明。

验证优先级：

1. 用户定义的业务验收；
2. 仓库内已有规则和测试；
3. Charter 新增的场景测试；
4. 构建、类型、静态分析和安全检查；
5. 人工或 Agent 的体验审查。

不能因为完整测试耗时而静默跳过。若风险可接受，必须通过明确 Gate 记录部分验证和剩余风险。

### 5.4 单仓库约束的准确含义

“单仓库”只约束一个可独立验收的软件交付单元，不约束整个 Agent Company，也不把 Project 定义成仓库。

跨仓库目标可以属于同一个业务 Project，但必须拆成关联 Work Item 或交付单元。每个单元分别拥有：

- 写入范围与负责人；
- 基础提交和 Worktree 生命周期；
- 验收、Review 和审批；
- 合并顺序、依赖与失败处置；
- 最终聚合验收结果。

系统不得在一次未声明的执行中隐式修改多个仓库。

### 5.5 Worktree 生命周期

```text
Charter
→ Planned
→ Worktree Ready
→ Implementing
→ Testing
→ Agent Review
→ Waiting Approval
→ Merging
→ Verifying Main
→ Delivered
→ Worktree Destroyed
```

失败和取消是可恢复状态，不是销毁资源的快捷方式。

## 6. 失败与证据

失败不是只供后端诊断的日志，而是公司治理事实。每次尝试必须记录：

- 尝试序号与负责人；
- 输入、能力包、权限和资源快照；
- 发生了什么以及影响范围；
- 已产生的制品和证据；
- 失败原因、是否可重试和下一次调整；
- 升级对象、用户决策和现场处置。

主群聊只在失败改变计划、风险或需要用户介入时显示高信号投影。完整失败链保留在 Thread 的工作日志中，不能被成功重试覆盖。

## 7. 扩展新领域的条件

新领域不需要等待软件研发“完成后”才被允许存在，但进入默认产品体验前必须满足：

- 有清晰且持续的用户目标；
- 能复用通用工作契约；
- 有明确输入、制品和领域验证器；
- 权限、外部副作用和回滚可治理；
- 失败能留下证据并安全恢复；
- 不要求用户预先理解或手工编排固定 Agent 团队。

## 8. 非目标

- 用 Agent 模板数量代表领域能力；
- 为每个行业复制一套固定专家团队；
- 只有生成没有验证的“工作适配器”；
- 首次公开版本穷尽所有外部应用和行业细节；
- 为适配领域而弱化 Project、Gate、审计、私域或用户授权；
- 将软件交付的仓库约束误写成整个产品的边界。
