## 1. 背景与问题

### 1.1 当前状态

当前 LobeHub 群聊功能有两种发言者选择模式：

- **`auto`**：中央 LLM（host）观察对话并指定下一个发言者。这种方式在 agent 数量少时工作良好，但有明显的局限。
- **`round_robin`**：轮询方式，按固定顺序轮流发言，缺乏灵活性。

### 1.2 核心问题

**中央主持人模式的缺陷：**

1. **昂贵的广播式调用**：每次需发起一个广播式 system LLM 调用（分析所有成员的发言、做决策），成本高、延迟大。
2. **单点故障**：如果 host LLM 调用失败或超时，整个对话卡住。
3. **不自然的对话节奏**：真实的 IM 群聊中，成员主动发言而非被点名。主机模式产生的对话节奏不流畅。
4. **LLM 幻觉放大**：单个 LLM 同时观察 N 个 agent 的行为并分配发言权——当 LLM "幻觉"谁应该发言时，影响整个对话。

### 1.3 用户痛点

- **作为群聊参与者**：我不希望被一个"主持人"指定发言，而是像在真实群聊中一样，在合适的时候主动说话。
- **作为产品经理**：我希望 agent 之间的对话看起来像真实的团队讨论，而非刻板的轮询或主机点名。
- **作为技术负责人**：我不希望每个群聊对话都需要一个昂贵的广播 LLM 调用，资源消耗不可控。

## 2. 产品目标

### 2.1 产品愿景

构建一个**类人化的多 agent 群聊系统**，使 agent 之间的协作对话看起来和感觉上像真实人类团队在一个 IM 群组中的交流——自然、有序、高效，且不需要一个"主持人"来管理对话。

### 2.2 核心原则

1. **无主持人**：不依赖中央 LLM 来选择谁发言。
2. **自然对话流**：agent 在有意愿的时候主动发言，而非被点名。
3. **低延迟低成本**：使用廉价的意图探测（intent probe）替代完整的 LLM 决策。
4. **公平且高效**：确保所有成员都有机会表达，同时不让单一成员垄断对话。
5. **安全降级**：任何组件故障都不应导致整个对话崩溃。

### 2.3 成功指标

| 指标 | 目标 | 测量方式 |
|------|------|----------|
| 每轮调度延迟 | < probe 最慢 LLM 调用 | 通过日志监控 |
| 对话自然度 NPS | > 4.0 / 5.0 | 用户调研 |
| agent 发言覆盖率 | 每 10 轮中 ≥ 60% agent 发言 ≥ 1 次 | 内部统计 |
| 无主机参与率 | 100% | 日志验证，无 host 类型指令 |
| 最大沉默轮次 | < 2 轮（当有人类输入时） | E2E 测试 |

## 3. 用户画像与场景

### 3.1 用户画像

| 画像 | 角色 | 需求 |
|------|------|------|
| **产品经理 (PM)** | 配置 agent 团队进行讨论 | 让 agent 像真实团队一样讨论，产生有价值的决策洞察 |
| **开发者 (Dev)** | 集成 agent 群聊到产品 | 可预测的行为、清晰的接口、可靠的降级机制 |
| **最终用户 (User)** | 与 agent 团队对话 | 自然的对话体验，不需要手动指定谁发言 |

### 3.2 使用场景

#### 场景 1：创业团队战略讨论

> 用户创建一个董事会（CEO/CTO/CFO/CMO），问"我们想做一个 AI 资讯网站，大家有什么想法？"

**期望行为**：
- CMO 从市场角度先发言（话题相关度最高）
- CTO 接着从技术可行性发言
- CFO 评估成本预算
- CEO 做产品方向总结
- 所有成员轮流发言，没人垄断

**预期体验**：
- 对话像真实的团队讨论
- 每个成员的观点自然衔接
- 用户不需要干预谁应该说话

#### 场景 2：技术方案评审

> 用户提出"我们考虑用微服务架构重构后端，CTO 觉得怎么样？"

**期望行为**：
- CTO 因为被直接点名，大概率投 `must` 或 `want`
- 其他成员基于相关性决定是否参与
- 反对意见（如涉及成本、开发周期等）被其他成员提出

#### 场景 3：任务执行与汇报

> CEO 说"我们需要调研竞品的 SEO 策略"

**期望行为**：
- CMO 认领任务（`claim`）
- 执行任务后汇报结果
- 其他成员基于结果展开讨论

#### 场景 4：模型降级（可观测性）

> 某个 agent 的 probe LLM 不可用

**期望行为**：
- 该 agent 安静（`pass`），不影响其他人
- 对话继续，其他 agent 正常出价
- 用户不会被错误的中断或死寂困扰

### 4.2 需求详情

#### F-01: bidding 发言者选择模式

**描述**：群组配置增加第三种发言者选择模式 `bidding`，与已有的 `auto`、`round_robin` 并列。

**接受标准**：
- [ ] 创建群组时 `speakerSelectionMethod` 可选 `bidding`
- [ ] 选择 `bidding` 模式后不创建 host（主持人）agent
- [ ] 与现有群聊系统无缝集成
- [ ] 向后兼容——现有群组不受影响

**配置示例**：
```json
{
  "groups": [{
    "name": "董事会圆桌会议",
    "speakerSelectionMethod": "bidding",
    "members": ["ceo", "cto", "cfo", "cmo"]
  }]
}
```

#### F-02: 并行意图探测

**描述**：所有 agent 收到探测请求时，并行调用廉价的 intent probe LLM，仅决定是否要发言，不生成发言内容。

**接受标准**：
- [ ] 所有 agent 的 probe 调用并行发起
- [ ] probe 返回速度不会因单个 agent 延迟而阻塞所有人
- [ ] probe 输出仅包含 4 个字段（level, type, addressedAs, reason）
- [ ] 不探测 host（因为没有 host）

#### F-03: 确定性仲裁

**描述**：基于出价评分系统，确定性（非随机）选择本轮发言者。

**接受标准**：
- [ ] 给定相同输入，仲裁总是输出相同结果
- [ ] 评分基于双层公式：IntentLayer + RightsLayer
- [ ] `pass` 级别总是排除
- [ ] 低于 τ（阈值）的 base 值总是排除

#### F-04: 冷却机制防止独白

**描述**：发言后 agent 获得冷却（cooldown）惩罚，在一段时间内不太可能再次发言。

**接受标准**：
- [ ] 发言后 cooldown 设为最大值（默认 50）
- [ ] 每轮 cooldown 衰减 15，直到归零
- [ ] 刚发言者即使投 `must` + `objection`，也低于别人的 `want`
- [ ] 连续两轮不会由同一个 agent 发言

#### F-05: 久沉默加分拉入

**描述**：长时间未发言的 agent 获得 staleness 加分，鼓励其参与。

**接受标准**：
- [ ] 每 idle 一轮获得 +5 分
- [ ] 加分有上限（默认 30），不会因此独占
- [ ] 久沉默者的出价因加分更容易胜出

#### F-06: Human Fallback 防死寂

**描述**：用户消息后如果所有 agent 都 `pass`，自动选择一个"最欠发言"的 agent 回应。

**接受标准**：
- [ ] 人类输入后，即使全员 `pass`，也有至少一个 agent 回应
- [ ] 选择算法基于 `idleRounds - cooldown` 最大者
- [ ] 每次选择轮换（不总是同一个人）
- [ ] Agent 触发的轮次（`agent_spoke`）可以安静结束，不触发 fallback

#### F-07: 连续发言预算（K 值）

**描述**：agent 连续发言 K 轮后自动停止，让人类用户介入。

**接受标准**：
- [ ] 默认 K=6 轮
- [ ] 达到 K 后发射 `turn.yielded` 事件
- [ ] 人类发送新消息后 budget 重置
- [ ] 任务完成（`task_completed`）重置 budget

#### F-08: Probe 安全降级

**描述**：意图探测的任何失败都安全降级到 `pass`，不会导致对话异常。

**接受标准**：
- [ ] LLM 调用超时 → `pass`
- [ ] LLM 返回非法 JSON → `pass`
- [ ] `level` 字段无效 → `pass`
- [ ] 仅 `type` 或 `addressedAs` 无效 → 强制设为安全默认值

#### F-09: 任务完成重置预算

**描述**：agent 执行任务完成后，新结果视为"外部输入"，重置连续发言计数器。

**接受标准**：
- [ ] `task_completed` 事件将 `consecutiveAgentTurns` 重置为 0
- [ ] 重置后重新出价循环

## 5. 功能规格

### 5.1 评分公式

**最终分数 = 意图层 + 权利层**

```
Score = base(level) + addressBonus(addressedAs) + typePriority(type) - cooldown + staleness(idleRounds)
```

**资格条件**：`level !== 'pass'` 且 `base(level) >= τ`

#### 意图层基数（默认值）

| level | base | 说明 |
|-------|------|------|
| `must` | 100 | 强力发言意愿 |
| `want` | 60 | 中等发言意愿 |
| `could` | 30 | 一般发言意愿 |
| `pass` | — | 不参与竞标 |

#### 被点名加分

| addressedAs | 加分 | 说明 |
|-------------|------|------|
| `direct` | 40 | 被直接点名 |
| `mention` | 15 | 被提及 |
| `none` | 0 | 未被点名 |

#### 类型优先级加分

| type | 加分 | 说明 |
|------|------|------|
| `objection` | 15 | 反对/风险发现 |
| `answer` | 10 | 直接回答问题 |
| `question` | 6 | 关键性问题 |
| `claim` | 4 | 认领任务 |
| `info` | 2 | 补充信息 |
| `support` | 0 | 附和/支持 |

#### 权利层参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| cooldownInitial | 50 | 发言后冷却初值 |
| cooldownRecoverPerRound | 15 | 每轮冷却恢复 |
| stalenessPerRound | 5 | 每 idle 轮加分 |
| stalenessCap | 30 | 加分上限 |
| tau (τ) | 30 | 资格门槛 |
| K (maxConsecutiveAgentTurns) | 6 | 最大连续发言轮次 |

### 5.2 用户界面需求

#### 前端展示（Phase 2）

- [ ] 当前发言者高亮显示
- [ ] 出价历史可视化（可选）
- [ ] 当前调度阶段指示器（idle / bidding / speaking）
- [ ] 谁正在发言的标识
- [ ] 对话进入"发言权竞价"阶段时的 UI 提示

#### 配置界面

- [ ] 群组配置中可选择 `bidding` 模式
- [ ] 可选的高级配置面板（tau, K 值, cooldown 等—默认折叠）

### 5.3 事件日志

调度器发射的事件应记录到日志，便于排查和可观测性：

```json
{ "type": "bidding.opened",       "round": 3, "eligibleAgentIds": ["ceo", "cto"] }
{ "type": "bid.submitted",        "agentId": "ceo", "bid": {...}, "finalScore": 85 }
{ "type": "speaker.elected",      "agentId": "ceo", "round": 3, "finalScore": 85 }
{ "type": "turn.yielded",         "reason": "budget_K_reached" }
```

## 6. 非功能需求

### 6.1 性能

| 需求 | 目标 |
|------|------|
| 每轮探测延迟 | ≤ probe LLM P99 响应时间 |
| 仲裁计算时间 | < 1ms（N ≤ 20） |
| 内存占用 | < 5MB/频道 |
| 前端事件更新延迟 | < 200ms |

### 6.2 可靠性

| 需求 | 目标 |
|------|------|
| Probe 降级率 | ≤ 5% 正常调用返回 pass |
| 仲裁成功率 | 100%（确定性算法） |
| 无死寂率（有人类输入时） | 100% |
| 错误恢复 | 下一个人类消息自动重置 |

### 6.3 可观测性

- 支持通过事件日志追踪每个轮次的完整决策链路
- 关键指标应有 Prometheus/Metrics 上报（每轮延迟、probe 成功率、distinct speaker 分布、idle 比例）

### 6.4 兼容性

- 与现有的 `auto`、`round_robin` 模式完全独立
- 后端新增 `bidding` 配置即可切换模式，无需修改现有群聊逻辑

## 7. 验收标准

### 7.1 核心路径验收

```
GIVEN 一个有 4 个 agent 成员且模式为 bidding 的群组
WHEN 用户发送一条消息
THEN 所有 agent 同时被探测，展示"竞价中"状态
AND 一个 agent 被选出发言
AND 其他 agent 安静等待
AND 流程重复直到无人想发言或达到 K 值
AND 用户始终可以插入新消息
```

### 7.2 公平性验收

```
GIVEN 一个 agent 连续发言了
WHEN 该轮结束后结算权利
THEN 该 agent 的冷却值升高，下轮不太可能再次发言
AND 久未发言的 agent 获得加分
AND 在几轮后所有 agent 都有机会发言
```

### 7.3 鲁棒性验收

```
GIVEN 某个 agent 的 probe LLM 完全失效
WHEN 触发一轮竞价
THEN 该 agent 自动 pass（不出价）
AND 其他 agent 正常出价
AND 对话继续
AND 没有任何 UI 错误或崩溃
```

### 7.4 降级验收

```
GIVEN 所有 agent 都 pass
WHEN 触发的原因是 human 消息
THEN 系统自动选出"最欠发言"的 agent 作为 fallback 发言人
AND 对话不会死寂
AND fallback 发言人非 host
```

## 8. 边界场景与异常处理

| 场景 | 期望行为 | 优先级 |
|------|----------|--------|
| 所有 probe LLM 超时 | 全员 `pass` → fallback 选最欠发言者回应 | P0 |
| 部分 probe LLM 超时 | 超时者 `pass`，其他正常 | P0 |
| 所有 agent 连续发言 K 轮 | yield to human，等待用户输入 | P0 |
| 用户快速连续发送消息 | 每次触发一轮新 bidding，budget 重置 | P1 |
| 群组只有 1 个 agent | 直接选他发言（无需竞价） | P1 |
| 群组有 20+ agent | 仲裁仍 O(N log N)，probe 并行 | P2 |
| 同一轮两个 agent 分数完全一样 | tie-break：idleRounds 大者优先 | P0 |
| 协作者务被认领后，又有人想认领 | 认领优先级低 (`typePriority.claim=4`)；已在运行的认领被 probe prompt 禁止重复 | P0 |
| agent 被点名但同时不想说话 | `pass` 是合法选项——点名不强制发言 | P0 |
| 某 agent 持续不参与（永远 pass） | 正常行为——staleness 加分直到 cap 30；probe prompt 会提示"你很久没发言" | P1 |
| 对话进行数小时后 | 状态持续累积，无 window 重置——长期运行需注意冷却/权重的合理性 | P2 |
| 频道被删除 | 相关 SchedulerState 清理 | P1 |

## 9. 成功指标

### 9.1 定量指标

| 指标 | 目标 | 度量工具 |
|------|------|----------|
| **发言者多样性** | 每 10 轮中，≥75% 的成员至少发言 1 次 | 调度器事件统计 |
| **沉默率（有人类输入时）** | 0%——永远有回应 | event log |
| **K 值触发率** | < 20% 的对话 session 达到 K 值（自然结束为主） | event log |
| **probe 成功率** | > 95%（5% 以内降级到 pass 算正常） | probe log |
| **平均每轮延迟** | < p95 probe LLM latency | metric |

### 9.2 定性指标

- **对话流畅度**：用户调研——对话是否看起来像真实的团队讨论？
- **参与公平性**：观察是否有 agent 长期被"排挤"而无法发言
- **自然停顿**：agent 对话中是否有符合上下文的短暂停顿（而非机械的不间断发言）

### 10.1 当前开放问题

| 问题 | 状态 | 需要决策方 |

| probe 使用什么模型？是否可配置 vs 固定用主模型？ | 待定 | 架构团队 |

| 长期对话中的时域衰减（长时间窗口后的重置策略）？ | 待定 | 技术团队 |

### 10.2 未来规划

| 阶段 | 特性 | 时间 |
|------|------|------|
| **Phase 1** | 核心 bidding 调度器实现 + 测试 ✅ 已完成 | v0.1 |
| **Phase 2** | 前端状态投影 + UI 展示 | v0.2 |
| **Phase 3** | 参数在线可调（无需重启） | v0.3 |
| **Phase 4** | 基于 event replay 的自动参数调优 | v0.4 |
| **Phase 5** | 混合模式：auto + bidding 自适应 | v1.0 |

### 10.3 未来的模式扩展

- **加权 bidding**：不同 agent 分配不同权重的出价（如 CEO 的 `must` 比 CTO 的 `must` 更高权重）
- **优先级议题**：强制要求在议题 A 讨论完之前，不跳转到其他议题
- **角色约束**：某些类型的问题仅特定角色可以发言（如仅 CFO 能讨论预算）
- **人类干预**：用户可以在竞价阶段手动指定下一位发言者，覆盖自动仲裁

## 附录 A：术语表

| 术语 | 定义 |
|------|------|
| **Bidding** | 自主竞价调度机制，agent 通过出价竞争发言权 |
| **Probe** | 意图探测，廉价的 LLM 调用，仅决定是否要发言 |
| **Bid** | 投标单，包含 level/type/addressedAs/reason |
| **Level** | 发言意愿强度：must / want / could / pass |
| **Type** | 贡献类型：objection / answer / question / claim / info / support |
| **Arbitration** | 确定性仲裁，基于打分结果选择发言者 |
| **Cooldown** | 冷却惩罚，发言后被施加，抑制连续发言 |
| **Staleness** | 久沉默加分，长时间不发言者获得竞争加权 |
| **K (Budget)** | 最大连续 agent 发言轮次 |
| **τ (Tau)** | 资格门槛阈值，base(level) 低于 τ 的投标不参与竞争 |
| **Fallback** | 降级机制：human 输入后全员 pass 时选最欠发言者回应 |
| **Rights Layer** | 权利层，跨轮次的持久化状态（cooldown + idleRounds） |
| **Intent Layer** | 意图层，每轮重新探测的出价得分 |
| **Yield to Human** | 达到 K 值或无人竞标时，将发言权交还给人类用户 |
