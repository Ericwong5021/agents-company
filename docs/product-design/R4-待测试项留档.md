## R4 TEAM-02 — Capability Evidence 与 Runtime Compatibility 模型  `[已实现]`

**实现位置**
- `packages/control-plane/src/company-recruitment/capability-evidence.ts`（新增）：纯函数证据层。`evidenceStatus`（declared/verified/expired 三态推导，30 天验证 TTL）、`runtimeCompatibility`（Runtime 能力硬门）、`capabilityAvailability`（能力包存续 × Runtime 兼容）、`declaredPacksFromProfile`（存量 Agent Profile → 初始 declared 能力迁移）。
- `packages/control-plane/src/runtime/capability-matrix.ts`（新增）：`RuntimeCapabilityMatrix` 静态声明 pi / claude-code / codex 三个 Runtime 的 14 项能力事实，供 Runtime 适配层与团队选择共用；`missingRuntimeCapabilities` 计算缺口。
- `packages/control-plane/src/company-recruitment/`（schema.ts / sql.ts / company-recruitment.ts 改造）+ migration `20260728000000_company_agent_capability`：能力证据落库；运行成功/失败回写 `last_verified_at` / `failure_count` / `last_failure_at`。
- `packages/control-plane/src/company-project/execution.ts`：缺少必需能力包证据的 Agent 不进入主执行者候选。

**设计要点与现状**
- 证据状态与可用性**正交**：declared/verified/expired 描述“证据新鲜度”，available 描述“能力包仍在目录且 preferred Runtime 满足要求”；能力包退役或 Runtime 缺能力时读作不可用，不当作确定能力展示。
- verified 超过 30 天 TTL 自动回落为 expired，陈旧成功不会一直读作当前能力。
- 失败只累加 `failure_count` 并记录时间，不清除既有验证，失败不会简单永久否定能力。
- 能力包引用解析失败（退役/未知包）不抛错，读作证据不可用，不炸投影；ad-hoc 包名在选择硬门中保持中性。
- 迁移路径：`declaredPacksFromProfile` 按 role/description/skills/responsibilities 与目录包的确定性匹配生成初始 declared 能力，不虚构 verified。

**开发者自测结论**：`bun test test/company test/company-recruitment test/conversation test/company-agent test/company-project`（packages/control-plane）→ 129 pass / 0 fail；`bun typecheck`（tsgo）EXIT=0。

### 待专人测试项
- [ ] 模型测试：同一 Agent 依次经历 声明未验证 → 首次成功（verified）→ 30 天后（expired）→ 能力包下线（不可用），四态展示与时间推导正确。
- [ ] 选择测试：相同角色名但 preferredRuntime 不同的两个 Agent，对需要特定 Runtime 能力的任务得到不同可用性结论。
- [ ] 历史更新测试：成功刷新 last_verified_at；返工/失败累加 failure_count 但不清除 verified；规则符合预期。
- [ ] 迁移测试：对存量 Agent Profile 首次运行后生成初始 declared 能力，且不出现凭空 verified。
- [ ] UI 验证：Agent 详情能看到每项能力的来源（declared/verified/expired）与最近验证时间；无证据支持时不显示“专家”式确定标签。

## R4 TEAM-03 — 风险驱动的动态编排与验证强度  `[已实现]`

**实现位置**
- `packages/control-plane/src/company-project/orchestration.ts`（新增）：纯规则层。四档验证强度 `self_check / auto_verify / independent_review / review_with_gate`；`orchestrationPlan` 综合 work_type、申报风险、审批模式推导最终强度并输出 reasons + alternatives。
- `packages/control-plane/src/company-project/execution.ts`（改造）：编排接线规则层决策——由规则层而非 planner 标签决定风险与验证强度。
- `packages/control-plane/test/company-project/orchestration.test.ts`（新增）：策略矩阵单测。

**设计要点与现状**
- 风险地板（rule floor）：coding 写入用户主仓库并合并主分支，规则层恒定视为 high，模型错误标注 low 也无法降级——提示词改动无法绕过强制复核/Gate。
- 强度映射：low → 自检；medium → Work Type 结构化自动验证（不再无条件创建 Reviewer）；high → 独立 Reviewer；high + coding + 非 autonomous 审批 → Reviewer + 用户 Gate。
- strict 审批模式将验证强度**单向提升一档**，任何配置都不能把高风险任务降到独立复核以下。
- 每次编排记录采用该强度的中文事实性原因与全部替代方案（低于要求的标注“被规则层拒绝”，高于要求的标注延迟/成本代价），满足决策可审计。

**开发者自测结论**：orchestration.test.ts 随 control-plane 全量 129 pass / 0 fail；`bun typecheck` EXIT=0。

### 待专人测试项
- [ ] 策略矩阵：风险（low/medium/high）× work_type × 审批模式（autonomous/balanced/strict）组合的实际编排路径符合计划文档预期。
- [ ] 绕过测试：构造让模型把 coding 任务标为 low risk 的输入，确认规则层仍提升为 high 并保留独立复核 + Gate。
- [ ] 回归测试：research / writing / analysis 等非 coding 任务不再无条件创建 Reviewer，交付质量不下降。
- [ ] 成本对比：低风险任务相较旧固定 Worker+Reviewer 流程，中位延迟和模型调用次数显著下降（需真实模型环境采样）。
- [ ] 审计验证：Diagnostics/决策记录中能看到编排原因和替代方案，内容为事实性描述而非模型私有推理。

## R4 TEAM-04 — 候选评分、选择理由与拒绝理由重构  `[已实现]`

**实现位置**
- `packages/control-plane/src/company-recruitment/selection-policy.ts`（新增）：纯函数两阶段选择层。`hardGaps` 硬约束门（独立性冲突 / Runtime 不兼容 / 既无可用证据也无画像匹配）、`evidenceStrength`（verified 100 > declared 60 > expired 30，不可用记 0）、`selectionScore` 九维评分（能力匹配、证据强度、负载可用性、历史质量/可靠性、成本、速度、风险适配、复用价值）、`compareCandidates` 确定性同分规则（总分 → 证据 → 能力 → 负载 → agent_id 字典序）、`softGaps` 落选者事实性维度差距、`unverifiedRequiredPacks` 入选者已知缺口。
- `packages/control-plane/src/company-recruitment/company-recruitment.ts`（改造）：`candidateFacts` 只收集可验证事实，评分与硬约束全部下沉到纯策略层。
- migration `20260728010000_team_selection_rank_gaps`：选择结果持久化 rank、选择理由、缺口与第二候选。

**设计要点与现状**
- 硬约束先于软评分：任何硬性缺口（工具/Runtime/独立性）直接失格，得分再高也不能入选（“高分买不回硬缺口”）。
- 高风险任务的 risk_fit 偏向正式员工或高质量高可靠历史，替代原先 Role/词项重合的浅层匹配。
- 拒绝理由是逐维度的事实句（“能力证据强度 X 低于入选者 Y”），不再只有字符串匹配得分；入选者未验证的必需能力包保留为可见缺口，不被总分吞掉。
- 无人满足硬性条件时走临时角色创建路径（TEAM-05），不强行选人。
- 计划文档“不在范围”遵守：完整评分公式与内部 Prompt 不向终端用户暴露，用户可见的是 Diagnostics 中的简洁事实理由。

**开发者自测结论**：company-recruitment 相关单测随 control-plane 全量 129 pass / 0 fail；`bun typecheck` EXIT=0。

### 待专人测试项
- [ ] 场景测试：高能力高负载 vs 中能力空闲、低成本低质量 vs 高成本高质量、工具不兼容高分候选——入选/落选与理由符合直觉且事实准确。
- [ ] 稳定性测试：同一公司快照重复触发选择，入选者、排名与理由完全一致。
- [ ] 审计测试：Diagnostics 中的选择理由能回指能力证据（pack + 状态）与运行时状态（负载数字），不出现模型私有推理。
- [ ] 硬门测试：缺少必需工具/权限的候选无论其它维度多高都不入选，且缺口以用户可读句子呈现。
- [ ] 无人达标：所有候选都有硬缺口时确认走临时角色/请求配置，不出现强行选人。

## R4 TEAM-05 — 临时角色/候选人/员工生命周期与 DRI 放宽  `[已实现]`

**实现位置**
- `packages/control-plane/src/company-recruitment/company-recruitment.ts`（改造）+ migration `20260728020000_employment_review_retired`：生命周期推进——临时角色实例释放时，只有沉淀真实任务证据（本项目已完成工作项或任意项目成功交付）才进入候选池；无证据直接退役（archive）并写审计记录。
- `packages/control-plane/src/company/activity.ts`：组织视图投影 `employment: "employee" | "temporary"`（在岗临时实例 = assigned 且活跃入选来源为 new_candidate），在岗临时实例与正式员工同屏可见但身份区分。
- `packages/control-plane/src/conversation/conversation.ts`（改造）：新增 `ensureThreadAccess`——非 Board 成员被指派 DRI 时按需授予源 Thread 的 channel + thread 成员资格，幂等可重入。
- `packages/control-plane/src/company-project/execution.ts`（改造）：DRI 不再强制为 Board 成员，签署前与读取源 Thread 证据前自动确保成员资格。
- Reviewer 独立性由 TEAM-03 规则层按风险决定（低风险无独立 Reviewer；高风险执行者与复核者互斥由选择硬门的独立性约束保证）。

**设计要点与现状**
- 四种身份对应真实生命周期事实：temporary role instance（assigned + new_candidate 来源）、candidate（候选池）、employee（正式员工）、board member；不再每个任务自动铸造“只有名字和 Prompt 的正式员工”。
- 晋升/复用/退役全部留审计记录；重复类似任务时选择层的 reuse_value 维度优先复用合格候选。
- DRI 放宽以能力与权限为准；成员资格授予是最小必要（源 Thread），不是全局提权。

**开发者自测结论**：conversation / company-recruitment / company-project 单测随 control-plane 全量 129 pass / 0 fail；`bun typecheck` EXIT=0。

### 待专人测试项

- [ ] 无证据退役：临时角色未完成任何工作项即释放时直接退役，不进入候选池，且有审计记录。

- [ ] 组织视图：Team 页面临时实例与正式员工身份标识正确，临时实例任务结束后不再出现在团队视图。
