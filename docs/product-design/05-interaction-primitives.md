# IM-first 交互与协作原语

> 状态：当前
> 上位文档：[产品宪法](PRODUCT-CONSTITUTION.md)

## 1. 交互原则

用户应该感觉自己在经营一家公司，而不是操作一个多 Agent 控制面板。

- 对话是主入口；
- 结构化信息由系统从对话中形成；
- 重要结果主动浮到主会话；
- 完整过程可展开但不默认打扰；
- 所有高风险动作都能看懂“谁要做什么、为什么、影响什么”。

## 2. 工作台布局

推荐桌面结构：

```text
┌──────────────┬───────────────────────────────┬────────────────────┐
│ 公司与频道   │ 群聊主会话                     │ Context Panel      │
│              │ 高信号消息 / 决定 / 审批 / 交付 │ Thread / 人员 / 制品│
│ 公司大群     │                               │ 当前 Thread        │
│ 董事会       │  └─ 展开 Thread               │ 风险 / 待办        │
│ 部门         │      └─ 展开 Tool details      │                    │
│ 项目         │                               │                    │
│ Direct       │ 输入框 + @ + /action           │                    │
└──────────────┴───────────────────────────────┴────────────────────┘
```

右侧 Context Panel 可以折叠。看板、组织图、制品库和审计是独立查询视图，不占据默认主舞台。

Thread 面板至少包含工作日志、产出物和预览三个稳定入口。失败尝试、工具调用和中间讨论进入工作日志；文档、代码、数据和其他制品进入产出物；能够安全渲染的结果进入预览。群聊只显示这些内容形成的高信号结论和状态变化。

### 2.1 呈现层参考与技术边界

董事会和项目协作的呈现层以 `yetone/cumora@5dbbdee15b66e9f3faa52aacad14e8e27fe583e1` 为固定视觉与交互参考。布局密度、会话列表、消息时间线、Composer、Thread、Info 和 Artifact 面板在 Vue/Nuxt 中重写，Agent Company 的 Control Plane、领域模型、API、实时事件、权限、治理与工作流继续作为唯一业务事实源。

不得引入 React 子应用、Cumora 状态管理、后端、数据库或 Agent Runtime。UI 组件只接收 ViewModel 并发出用户意图，不直接请求 API 或订阅实时事件。迁移先完成董事会纵向切片，再复用到 Work 和 Operations；在首个纵向切片可用前，不同时改造其他业务页面。

## 3. 频道

| 频道 | 常驻成员 | 主要内容 | 正式记录责任 |
|---|---|---|---|
| 公司大群 | 正式员工；候选按需 | 公告、文化、跨项目高信号动态 | 只保留组织级信息 |
| 董事会 | 用户、CEO、CTO、Product Lead | 目标、Charter、战略、重大升级 | 决定和立项必须结构化 |
| 部门群 | 部门成员 | 能力建设、跨项目职能协作 | 职业与部门决定 |
| 项目群 | 项目团队 | 交付主场 | 范围、任务、风险、决定、制品 |
| Direct | 两个 Agent；用户只读 | 私人交流和关系发展 | 正式工作内容需摘要回项目群 |

## 4. 主会话高信号协议

默认显示以下消息类型：

- `conclusion`：讨论形成的结论；
- `decision`：有 DRI 的正式决定；
- `plan`：Charter、里程碑或计划更新；
- `status`：阶段变化、完成或暂停；
- `risk`：新增或升级风险；
- `approval`：需要用户处理的事项；
- `delivery`：制品、审查和验证结果；
- `intervention`：用户越级、暂停、接管或策略变更。

寒暄、重复同意、工具日志、逐文件进度和中间方案默认留在 Thread 内。

每条高信号消息必须携带来源 Thread、作者/DRI、时间和相关项目；系统摘要不能变成没有来源的“公司说”。

## 5. Thread

Thread 是一个议题的完整协作容器，可以包含：

- 参与者与目标；
- 消息与提及；
- 子任务与委派；
- 方案比较和异议；
- 工具调用、日志、diff 与测试；
- 形成的结论、决定和制品；
- Token、耗时、状态和失败原因。

Thread 允许嵌套工作项，但 UI 避免无限树。默认只展开当前层，深层工具细节按需加载。

## 6. 卡片

结构化卡片嵌入会话，不打断 IM 连续性。

### 6.1 Charter Card

显示目标价值、交付物、验收、非目标、风险、DRI、里程碑和待决策项。允许用户只修改需要其决策的部分；董事会负责维护其余结构。

### 6.2 Approval Card

必须回答：

- 谁申请；
- 要执行什么；
- 为什么现在需要；
- 会修改哪些资源；
- 风险、成本和可逆性；
- 如果拒绝会怎样；
- 推荐选项与证据。

用户操作：批准一次、批准本项目同类动作、更新公司规则、拒绝并给出原因。

### 6.3 Delivery Card

显示交付物、领域验证证据、审查 findings、受管资源状态和剩余风险。软件交付额外显示合并目标、提交与 Worktree 状态。只显示“完成”而没有验证证据是不合法状态。

### 6.4 Agent Card

展示 Agent 自选公开 PROFILE 和系统签名事实。私人空间有独立只读入口，不应直接铺在公开名片上。

### 6.5 Employee Activity Card

员工卡片是公司的实时状态面，至少显示：

- 身份、当前责任和所在团队；
- 当前行为、对象、位置和协作同伴；
- 开始时间、可打断性和风险；
- 支撑状态的 Thread、Agent Run、Direct 或 Ambient 事件；
- 最近形成的制品、提案、关系变化或文化理解。

卡片必须能够区分正式工作、等待、Review、闲逛、社交、反思和做梦。后续办公室画面与卡片共用状态契约，不能自行编造活动。

### 6.6 Attempt Card

失败和重试在 Thread 工作日志中使用 Attempt Card 呈现。卡片包含尝试序号、负责人、输入与资源、失败原因、影响、已保留现场、是否可重试、下一次调整和升级记录。

后续尝试成功时，旧 Attempt Card 仍然保留。只有失败改变计划、扩大风险或需要用户介入时，才向群聊发布 Risk、Status 或 Approval 消息。

## 7. 协作原语

| 原语 | 含义 | 结构化副作用 |
|---|---|---|
| `message` | 告知，不要求交付 | 产生消息与可选通知 |
| `delegate` | 将可验收工作交给负责人 | 创建 Work Item、委派链与权限作用域 |
| `reply` | 回应请求或提交结果 | 关联原请求并更新未读/状态 |
| `propose` | 自下而上提出变化 | 创建提案，等待采用、搁置或拒绝 |
| `decide` | DRI 形成正式决定 | 固化选项、理由、异议和影响 |
| `escalate` | 当前层级不能安全继续 | 携带尝试、证据和建议向上流动 |
| `review` | 对照验收检查制品 | 生成 findings 与 Admission 结果 |
| `approve` | 允许高风险或受控阶段继续 | 写入授权范围与审计记录 |
| `interrupt` | 暂停、终止或接管 | 更新运行状态并安全释放资源 |

自然语言可以触发这些原语，但系统必须保存结构化结果。

## 8. 多 Agent 发言

群聊内部可以使用 Autonomous-Bidding 选择下一位发言者，以降低轮询噪音和单一 Agent 垄断。它是调度实现，不是用户必须理解的核心产品概念。

用户默认只看到自然的会话和必要的“正在形成结论”状态；评分、Probe 和调度日志放在 Thread 诊断层。具体见 [Bidding PRD](bidding-prd.md)。

## 9. Direct 交互

- 用户可在 Agent 页面只读打开 Direct；
- 用户查看不产生已读、提醒或上下文变化；
- 不提供把对方原话一键转发到群聊的动作；
- 当检测到工作承诺或范围变化时，系统提示参与者生成项目摘要；
- 摘要发布前明确显示将公开哪些工作事实。

## 10. 看板的角色

看板用于：

- 跨项目扫描状态；
- 查看阻塞、等待审批和负责人负载；
- 批量排序与筛选；
- 复盘历史流转。

看板不能成为创建所有工作的必经入口。用户从会话提出目标后，系统自动生成相应结构。

## 11. 通知与待办

只有以下事件默认通知用户：

- 需要用户审批或回答；
- 项目阻塞且无法自行升级；
- 高风险异常、预算越界或隐私/权限拒绝；
- 里程碑和最终交付完成。

普通 Agent 消息、每次任务完成和内部重试不应产生系统通知。通知点击后定位到对应高信号消息和 Thread。

## 12. 文案气质

- 工作结论像专业同事，Ambient、Direct 与私人空间允许更有个性和生活感；
- 清楚区分事实、推断、建议和决定；
- 报告风险时给出影响和下一步；
- 拒绝时说明边界，不伪造已执行；
- 人格化来自长期一致的身份、关系和真实经历；适度动画可以表达这些事实，但不能替代它们。
