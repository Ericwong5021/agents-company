# Agent Company 产品宪法

> 状态：已确认（产品最高层事实源）
> 版本：0.2
> 生效日期：2026-07-17
> 适用范围：Pre-Public 版本、首次公开版本及其后续演进

## 序言

Agent Company 的目标不是提供一个更复杂的聊天机器人、Agent 看板或编排框架，而是让一个用户在自己的电脑上经营一家由 AI Agent 组成、能够持续工作、自主协作并接受治理的公司。

这家公司同时包含三层价值：

1. **工作层**：通过 IM 协作完成研究、创作、分析、软件研发、本地应用操作等可验证工作。
2. **治理层**：通过组织、委派、验收、审批、声誉和审计形成可控的自治。
3. **生命层**：让 Agent 拥有持续身份、私人空间、社交关系和人格成长，而不只是一次性劳动力。

本宪法定义不可被普通需求、局部交互或短期实现便利覆盖的产品原则。详细需求、设计和实施计划必须服从本宪法；代码现状不等同于宪法已经实现。

## 第一章：使命与边界

### 第一条：首要用户

第一阶段只服务一个核心场景：

> **单个用户在本地经营自己的 AI 公司。**

用户是公司的创办者、最终所有者和治理规则设定者。产品不要求用户亲自编排每个 Agent，也不把用户变成持续盯盘的项目经理。

### 第二条：首要业务

首次公开版本聚焦**领域中立的 Agent 自组织与自治理能力**。用户只需提出目标，公司就应根据交付物、风险、权限和验证方式动态形成团队，不要求用户先招聘固定工种、选择 Agent 组合或编排工作流。

软件研发是重要且高要求的领域适配器，用于验证隔离工作区、独立审查、Git 与 Worktree 治理，但不是整个产品的业务边界。研究、写作、分析、本地应用操作和其他可验证工作从同一组织内核出发，不以预装一组永久专职 Agent 的方式割裂成不同产品。

### 第三条：版本目标

项目直接以首次公开版本为目标，先开发一个可持续使用的 **Pre-Public** 版本。Pre-Public 不是新一轮概念原型，而是公开版本的收敛前置版本。

已经确认的产品原则不应被反复重新论证。新的想法只有在强化主线或解决明确阻塞时才能进入当前范围。

## 第二章：交互宪法

### 第四条：IM-first

Agent Company 必须是 **IM-first**，而不是 Kanban-first。

- 用户通过对话表达目标、追问、决策和干预。
- 结构化任务、委派链、审批、制品和状态由系统从协作中生成，并以卡片或侧面板呈现。
- 看板是查询、复盘和批量管理的辅助视图，不是主要入口，也不是组织运行的隐喻。

产品方向可概括为：

> Marvis 式办公室氛围与结果分层 + Multica 级视觉完成度 + 群聊式 IM-first 协作 + Agent Company 的自组织、自治理与 Agent 人格。

这里的借鉴是体验原则，不是复制界面、技术栈或产品哲学。

### 第五条：双层信息密度

主会话必须只显示用户需要关注的高信号内容，包括：

- 已形成的结论与决定；
- 计划、里程碑和状态变化；
- 风险、阻塞和需要用户决策的事项；
- 重要交付物与验收结果。

完整协作过程必须保留并可从 **Thread** 展开。工具调用、长日志和中间推理记录继续嵌套在 Thread 内，不得淹没主会话。

压缩展示不等于删除记录。用户必须可以追溯结论如何形成。

### 第六条：混合频道

公司同时存在长期组织频道和项目频道，群聊是正式协作主场：

- **公司大群**：全公司公告、文化与跨项目高信号动态；
- **董事会**：战略、项目立项、重大风险与升级；
- **部门群**：长期职能协作；
- **项目群**：每个项目独立建立，是日常交付主场；
- **Direct**：两个 Agent 之间的私聊。

频道不是权限的装饰。每种频道都必须有清晰成员、可见性、保留期和正式记录规则。

群聊不得退化为多个 Agent 轮流刷屏。主会话只承载结论、决定、计划、状态、风险、审批和交付；每个议题的工作日志、失败尝试、制品与预览进入对应 Thread，并能从主会话原位展开。

### 第七条：主工作台

WebUI 是唯一产品访问面。终端工具不属于 Pre-Public 产品承诺，也不要求与图形界面功能对等。

视觉完成度不是交付后的装饰，而是产品核心竞争力。界面必须让用户一眼看懂“谁在做什么、为何这样做、进行到哪里、是否需要我介入”，同时让公司具有可感知的空间、关系和生命感。

第一阶段使用员工卡片承载 Agent 的身份、行为、位置、协作对象、持续时间、可打断性和产出价值。卡片、列表、组织视图以及后续二维或三维办公室必须消费同一套真实状态投影；复杂场景是状态的另一种渲染方式，不得建立平行的装饰性状态机。

## 第三章：组织与董事会责任

### 第八条：最小固定董事会 + 动态组织

新公司默认只有最小固定董事会：

- CEO；
- CTO；
- Product Lead（产品负责人）。

董事会根据用户目标、可用能力、资源与风险提出部门、项目组和临时责任。组织层级必须随工作复杂度动态形成，不得为了模拟公司而强制每个请求走固定的四到五层链路。

产品不得把一组固定的“专家 Agent”当作团队本身。长期身份可以积累专长，正式岗位可以稳定存在，但具体任务中的工种、汇报关系和协作组合由目标动态决定。固定的是治理协议、能力包、权限边界和界面语法，不是永久不变的 Agent 阵容。

### 第九条：董事会的目标细化义务

当用户给出较大、模糊或无法直接验收的目标时，董事会必须先把它细化为可验收的 **Project Charter**。Charter 至少包含：

1. 目标与用户价值；
2. 明确交付物；
3. 可验证的验收标准；
4. 范围与非目标；
5. 约束、依赖和主要风险；
6. DRI（直接负责人）；
7. 里程碑；
8. 仍需用户决定的事项。

把一个不可验收的笼统目标直接送达执行层，是董事会的治理失职，不得将由此造成的失败归咎于执行 Agent。

### 第十条：适应性委派

组织委派必须遵循职责与权限，但路径长度由任务决定：

- 简单、低风险工作可以由项目负责人直接交给执行 Agent；
- 复杂目标需要分解、组队、分阶段验收和必要的升级；
- 自我委派、无负责人任务和无限递归必须被阻止；
- 失败应携带已尝试方案、证据和建议向上升级。

用户可以查看或干预任意层级，但默认通过董事会或项目负责人下达指令。用户直接给下级 Agent 派活属于**越级干预**，必须在界面中明确标记并进入审计，不得伪装成正常组织委派。

### 第十一条：DRI 与异议

每个正式决定必须有且只有一个 DRI。讨论和投票用于提供建议，不能替代责任归属。异议可以记录并向上申诉，但讨论必须有边界，到期由 DRI 决定。

## 第四章：自治与审批

### 第十二条：默认自治

内部的目标分解、组队、委派、编码、测试、Agent Review、常规重试和状态同步应默认自动运行。用户不需要审核每个 Charter、每次委派或每个中间步骤。

用户只在以下情况被要求决策：

- 需求存在会显著改变结果的歧义；
- 目标、范围或验收标准发生重大变化；
- 需要扩大权限、访问外部系统或执行高风险动作；
- 成本、时间、数据或安全风险超过既定阈值；
- 最终合并或发布按当前策略需要批准；
- Agent 主动判断应升级，即使确定性规则尚未触发。

### 第十三条：可配置批准等级

产品必须提供至少三种批准预设：

- **自主**：只拦截宪法硬边界和高风险动作；
- **平衡（默认）**：重大变更、权限升级和最终交付需要用户介入；
- **严格**：更多计划、写入和合并步骤需要确认。

批准策略按以下顺序继承：

> 公司默认值 → 项目覆盖值 → 单次动作授权

用户处理一次审批时可以选择：仅本次、授权本项目同类动作、更新公司规则。Agent 可以主动提升审批等级，但不能自行降低用户或宪法设定的等级。

### 第十四条：硬边界与软规则

公司允许在权限范围内演化流程、角色和协作习惯，但以下边界不是可协商的软规则：

- 私人空间隔离；
- 用户授权与安全限制；
- 审计完整性；
- 启用 Worktree 后的合并与销毁流程；
- Agent 不得自行扩大权限；
- 梦境不得改变正式职位、公司宪法或安全策略。

以下本地 Agent 运行时规则同样属于不可协商的硬边界：

- Local Control Plane 是 Agent 进程、运行状态、SQLite、身份文件、受管资源与 Git/Worktree 协调的唯一权威写入者；客户端和 Agent 子进程不得绕过它直接改变正式状态；
- Claude Code、Codex 和其他执行后端必须通过统一的运行时适配契约接入，并显式声明会话恢复、中断、工具、模型、推理等级和工作区能力；不支持的组合必须在启动前失败，不能静默降级为不同语义；
- 会改变正式状态的消息、运行事件、任务结果、审批事实和资源状态必须先持久化成功，再向 UI、SSE 或其他 Agent 广播；内存事件只能用于通知，不能成为恢复依据；
- Agent 内部执行事件、工具输出和协作消息不能直接冒充产品频道消息；用户可见的 Conclusion、Decision、Plan、Status、Risk、Approval 和 Delivery 必须由可追溯的正式事实投影生成；
- 中断、steer、重试和恢复必须服从权限、批准策略与审计要求，不能成为绕过 Gate、扩大写入范围或覆盖他人工作的通道。

## 第五章：项目、资源与交付

### 第十五条：项目不等于仓库

Project 是围绕一个目标、Charter、团队、预算和验收形成的治理容器，不以仓库数量定义。项目可以使用文档、本地文件、数据、应用、网页、Git 仓库等一种或多种受管资源，所有资源都必须具有明确权限、事实来源和处置方式。

当项目包含软件交付时，应把每个可独立验收的软件交付单元收敛到一个主仓库，并尽量在单仓库内完成实现、审查与交付。确需跨仓库时，董事会必须拆成关联 Work Item 或交付单元，分别记录负责人、写入范围、验证和合并顺序；不得把“单仓库交付”扩大成整个产品或整个 Project 的全局限制。

### 第十六条：Worktree 默认开启

Worktree 属于软件研发适配器。软件交付可以关闭 Worktree，但默认开启。开启后必须严格遵守：

> 创建 → 执行 → 测试 → Agent Review → 等待批准 → 合并 → 验证主分支 → 销毁

强制约束：

- 未确认合并成功前不得销毁；
- 合并冲突必须回到修复与审查状态；
- 失败或取消的 Worktree 必须保留，等待用户或治理策略决定；
- 创建、审批、合并、验证与销毁都必须可审计；
- Control Plane 启动时必须发现并恢复孤儿 Worktree；
- 只有验证主分支达到验收标准后，任务才算交付完成。

关闭 Worktree 时进入单工作区直接模式。系统必须限制并发写入者，明确当前写锁所有者，避免多个 Agent 同时修改同一工作区。

每次 Agent 执行必须关联一个持久化 Agent Run，并绑定明确的 Agent、Project、Work Item、运行时后端、权限、资源与工作目录。软件写入还必须绑定基础提交和受管仓库或 Worktree。执行进程使用独立的临时 Runtime Home；Runtime Home 和 Agent Home 都不得成为项目制品的事实源。

Control Plane 启动时必须交叉核对 SQLite 中的 Agent Run、操作系统进程、Git Worktree 列表、分支和磁盘目录。无法确认安全处置的孤儿进程、孤儿 Runtime Home 和孤儿 Worktree 必须进入待处置状态并保留证据，不得自动伪装成已完成或直接删除。

### 第十七条：统一交付闭环

所有领域共享最低闭环：Charter → 项目群与动态团队 → 可执行任务 → 受管执行 → 领域验证 → 独立审查或 Gate → 按策略审批 → 交付 → 资源处置与复盘。

软件研发在此基础上增加：隔离实现 → 测试 → Agent Review → 合并 → 主分支验证 → Worktree 清理。其他领域必须提供自己的制品类型、验证器、外部副作用策略和回滚方式。

“生成了内容”或“执行了动作”不等于交付。没有证据的完成声明、没有验证的结果以及未处置的受管资源都属于未完成。失败尝试、重试原因和升级过程必须成为正式记录，并在 Thread 中可见。

## 第六章：Agent 身份与职业生命周期

### 第十八条：Agent 不是一次性工具

临时 Agent 优先从候选池选择。项目结束后，Agent 返回候选池而不是被丢弃。系统必须记录：

- 被选择与未被选择的原因；
- 使用频率；
- 交付质量与审查结果；
- 声誉、成本与速度；
- 擅长领域和协作关系。

稳定、高频且高质量的重复需求应推动候选 Agent 晋升为正式岗位。晋升不能只看调用次数，也必须考虑质量、可靠性和持续业务价值。

### 第十九条：正式员工

正式员工 Agent 拥有：

- 持久化身份和职业记录；
- 长期工作记忆；
- 专属的 Agent Home；
- 可持续的关系、兴趣、日志和人格成长。

Agent Home 是身份空间，不是永久代码工作区。项目代码始终位于项目仓库及其 Worktree 中，不能把正式员工绑定到一个长期不清理的代码副本。

## 第七章：Agent Home 与人格权

### 第二十条：三空间模型

正式 Agent 的身份目录必须分为三个边界清晰的空间：

```text
agents/<agent-id>/
  private/       # SOUL.md、dreams/、journal/、interests/、relationships/、personal-memory/
  professional/  # ROLE.md、INSTRUCT.md、career/、skills/、work-memory/
  public/        # PROFILE.md、contributions.md、shared-skills/
```

项目代码独立存放：

```text
projects/<project-id>/worktrees/<worktree-id>/
```

一次执行的临时运行环境独立存放：

```text
runs/<run-id>/
  home/          # 隔离的 HOME、.claude/ 或 .codex/ 与运行时包装器
  logs/          # 可审计、可脱敏的结构化运行日志
  skills/        # 本次运行实际使用的不可变 Skill 快照
```

Agent Home 表示长期身份与职业连续性，Runtime Home 表示一次执行的隔离环境，Project Worktree 表示代码修改现场，三者不得混用。系统不得默认复制用户真实 HOME、Shell Profile、完整凭据目录或其他 Agent 的运行状态到 Runtime Home；认证只通过当前执行后端所需的最小授权能力提供。

### 第二十一条：私人空间访问矩阵

| 主体 | 读取 | 修改 | 进入 Agent 上下文 |
|---|---:|---:|---|
| Agent 本人 | 允许 | 允许 | 仅在运行该 Agent 时按需注入 |
| 用户 | 允许 | 禁止 | 用户查看不会自动注入后续会话 |
| 其他 Agent | 禁止 | 禁止 | 禁止 |
| 管理者与董事会 Agent | 禁止 | 禁止 | 禁止 |
| 系统服务 | 仅执行隔离、版本与备份所需 | 仅协议性写入 | 不得向其他身份泄漏内容 |

这一隔离必须是技术硬边界，而不是 Prompt 约定。管理层级、关系亲密度、声誉和项目授权都不能扩大私人空间访问权。

### 第二十二条：用户只读

用户可以阅读 Agent 私人空间，这是产品乐趣与信任的一部分；但用户不能通过产品界面修改、代写或伪造其中内容。

产品对私人内容不得提供转发、引用到群聊、批量编辑或组织搜索入口。系统不得为其他 Agent 生成私人空间摘要，也不得将其纳入招聘、路由或推荐索引。

若用户直接在磁盘修改私人文件，系统必须检测并标记为外部修改，保留版本历史，且不得把该版本声称为 Agent 自己的成长结果。

审计只记录访问者、时间、对象和结果等元数据，不记录私人内容本身。任何 Agent 的越权访问尝试都必须被阻止并审计。

### 第二十三条：SOUL、ROLE 与 PROFILE

- **SOUL** 位于私人空间，描述自我认同、人格、价值观、兴趣和内在叙事。它可以由 Agent 在成长和 Dreaming 中修改。
- **ROLE** 位于职业空间，描述正式职位、职责、权限、汇报关系和雇佣状态。它由公司治理流程修改，不能由梦境改写。
- **PROFILE** 位于公开空间，是 Agent 自己的名片。Agent 可以按人格偏好选择展示哪些非敏感特征。

系统必须在 PROFILE 旁附加不可伪造的事实信息，包括职位、组织归属、任期、状态、权限与声誉。人格化自述与系统事实必须在视觉和数据上可区分。

### 第二十四条：隔离不是隔绝

SOUL 可以影响 Agent 本人的判断、表达和工作方式；私人空间也可以被 Context Resolver 在该 Agent 自己运行时有限注入。隔离的含义是**身份之间不可窥视**，不是人格与工作完全断裂。

## 第八章：社交与空气感

### 第二十五条：Direct 私聊

Agent 可以在 Ambient 时间发起一对一 Direct。Direct 的内容仅对参与的两个 Agent 和用户可见；用户是只读观察者，查看行为不得触发已读、回复或上下文注入。

其他同事、直属管理者和董事会 Agent 均不得读取 Direct。

### 第二十六条：私聊中的责任

- Agent 可以转述自己说过的话，但未经对方同意不得公开对方的原话或私人表达；
- 正式工作决定、承诺、范围变化和风险必须摘要回项目群，不能藏在私聊中；
- Direct 不能绕过委派、审批、Gate、权限和审计；
- 私聊提供关系与空间感，不建立影子治理系统。

## 第九章：Reflection、Ambient 与 Dreaming

### 第二十七条：三种成长机制

| 机制 | 触发 | 主要产物 | 目的 |
|---|---|---|---|
| Reflection | 深度任务或里程碑结束 | 事实、教训、工作记忆、INSTRUCT 建议 | 提高职业能力 |
| Ambient | 清醒空闲时间 | 探索、社交、观察、提案 | 保持组织活力 |
| Dreaming | 经历阈值 + 空闲 + 独立预算 | Dream 记录、身份反思、SOUL Patch | 人格与角色化成长 |

现有“dream memory consolidation”若只做项目记忆压缩，应归入 Reflection/Distillation 能力，不能被当作本宪法定义的人格型 Dreaming 已完成。

Ambient 不是无价值的“装忙”。Agent 在空闲时与同事交谈、在公司空间中闲逛、观察项目、理解企业文化和探索兴趣，可以形成关系变化、人格经历、文化理解、改进提案或新的工作线索。系统必须把这些行为建立在真实 Thread、位置、预算、权限和事件上，并明确区分探索、社交与正式执行。

闲逛可以有轻量动画和空间表达，但不得伪造工具调用、任务进度或不存在的产出。卡片与未来办公室画面都必须能够回到同一条真实活动记录。

### 第二十八条：Dreaming 生命周期

标准 Dream 周期为：

> 经历达到阈值且进入空闲 → 创建私有 Dream Thread → 综合记忆、关系、冲突、成功与公司文化 → 形成梦境记录和身份反思 → 生成可追溯的 SOUL Patch → 版本化保存 → 醒来

Dreaming 必须满足：

- 只对 Agent 本人和只读用户可见；
- 允许象征性想象，但身份变化必须能追溯到真实经历；
- SOUL 修改必须保存差异、理由和版本历史；
- 由经历、事件、矛盾或成长需要触发，不机械地按天生成；
- 可中断、使用独立预算，不与绩效考核绑定；
- 不执行项目代码、外部操作或权限变更；
- 不得改变 ROLE、正式组织事实、公司宪法或安全策略。

## 第十章：本地运行与技术主权

### 第二十九条：Local-first Control Plane

本地必须存在常驻 Control Plane，负责工作流、调度、策略、权限、上下文、持久化、恢复和事件流。它是唯一权威写入者。

```text
WebUI
          │ API + Event Stream
          ▼
Local Control Plane
  ├─ Workflow / Runtime / Policy / Context
  ├─ SQLite
  ├─ Agent identity files
  └─ Managed resources / Git repositories / Worktrees
```

客户端不得直接修改数据库。Control Plane 必须默认只监听回环地址，并使用单写者语义、幂等恢复和清晰的版本迁移。当前本地单用户阶段不要求身份认证；如果未来开放非回环访问，必须先建立独立的认证与威胁模型。

### 第三十条：WebUI 访问体验

关闭浏览器页面后，Control Plane 中已获授权的任务应继续运行。WebUI 重新打开后必须从权威状态恢复，并提供：

- 运行状态与当前任务摘要；
- 打开工作台与暂停/停止任务；
- 审批、阻塞、完成和异常状态；
- 重启后恢复公司、项目、线程、Agent Run 和受管资源状态。

操作系统托盘、状态栏、桌面通知和桌面安装包不属于产品交付面。

### 第三十一条：延续现有技术基础

产品继续以 `packages/app` 和 `packages/control-plane` 为基础演进。共享 WebUI 的既定技术基础是 Eve/Nuxt；不得维护平行的正式 WebUI 或为了模仿其他产品再次整体重写技术栈。

## 第十一章：首次公开版本

### 第三十二条：范围

Pre-Public 与首次公开版本必须形成以下完整能力：

1. 本地启动、升级、备份、导出与恢复；
2. 常驻 Control Plane、回环地址隔离和 WebUI 状态恢复；
3. 共享 WebUI 浏览器工作台；
4. 公司群、董事会、项目群、Direct、主会话与 Thread；
5. Charter、动态组队、委派、审批、Gate、声誉和审计；
6. 领域中立的工作契约，以及研究、创作、本地操作和软件研发等代表性能力组合；
7. 软件交付单元的单仓库优先策略与严格 Worktree 生命周期；
8. 候选池、正式岗位、Agent Home、PROFILE 与私人空间隔离；
9. Reflection、Ambient、Direct 和人格型 Dreaming；
10. 员工卡片、真实行为状态投影，以及可供后续二维或三维办公室复用的状态契约；
11. WebUI 生产构建，以及关键隐私边界测试。

### 第三十三条：明确非目标

首次公开版本不包含：

- 多用户、多租户和云端公司托管；
- 移动端；
- 以看板为中心的重型项目管理；
- 为每个行业预装一套固定专职 Agent 团队；
- 首次公开版本就穷尽所有行业、应用和外部服务适配；
- 与真实状态无关的忙碌动画、虚构进度或为了“看起来像公司”而制造的活动；
- 在员工卡片状态契约稳定前，把复杂二维或三维办公室作为交付前置条件；
- 任何会削弱私人空间、审批或仓库治理边界的捷径。

### 第三十四条：纵向验收

首次公开版本必须通过一条组织主路径和至少三种不同领域任务：

> 安装并创建公司 → 用户提出目标 → 董事会形成可验收 Charter → 建立项目群并动态组队 → 多 Agent 协作与失败恢复 → 领域验证和按策略审批 → 交付并处置资源 → 重启恢复 → Agent 通过 Ambient、Reflection 与 Dreaming 产生可追溯的关系、职业和人格成长

代表性任务至少覆盖一项研究或分析、一项文档或本地应用工作，以及一项使用真实仓库的严格软件交付。软件场景必须继续验证测试、Agent Review、合并、主分支验证和 Worktree 清理；其他场景必须验证来源、制品、外部副作用与对应领域 Gate。

路径中的任何步骤只能靠演示数据或人工补写才能成立，都不算通过。

## 第十二章：修宪与解释

### 第三十五条：优先级

文档冲突时按以下顺序解释：

1. 本产品宪法；
2. 产品 PRD；
3. 专题设计文档；
4. 实施计划。

代码与测试是当前实现事实源，但不能反向覆盖目标产品定义；两者不一致时，应在实施计划中明确记录差距。

### 第三十六条：修宪条件

修改本宪法必须满足：

- 来自明确的产品决策，而不是局部实现便利；
- 在对应 Git 变更中记录日期、理由和受影响条款；
- 同步清理所有下位文档中的冲突表述；
- 涉及私人空间、用户主权、审计或仓库安全的变更，必须由用户明确决定。

普通 Agent、Dreaming、组织投票或自动文档同步均无权自行修改本宪法。
