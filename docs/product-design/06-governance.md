# 06. 治理机制

> **模块**：治理机制
> **核心问题**：怎么评价、怎么决策、怎么进化
> **来源**：运转模型宪法 §1.3/§1.7/§1.8

## 1. 声誉 / 荣誉分

### 1.1 定位

荣誉分**不是管教 Agent 的激励**，而是**改变组织如何使用该 Agent** 的持久信号。

### 1.2 驱动什么

| 场景 | 作用 |
|------|------|
| **路由/选人** | 高分派重要活，低分派次要活或加强监督 |
| **组织进化** | 持续高分 → 晋升候选；长期低分 → 再培训/调岗/裁撤 |
| **提案权重** | 高声誉意见权重更高 |
| **招募** | Leader 优先挑高分 |
| **产品质感** | 办公室一眼看出谁靠谱 |

### 1.3 评分机制

| 类型 | 说明 |
|------|------|
| **大头自动算** | 准入是否通过、修复迭代轮数、用了几种方案、是否触红线、token 效率 vs 预估 |
| **小头上级 rubric** | 对固定标尺的主观评分 |
| **难度加权** | 挑硬任务部分成功不应比躺易任务扣得更狠 |
| **reviewer 担责** | 放过的活后被发现烂 → 扣 reviewer 的分 |
| **衰减/近期性** | 反映近期表现，可恢复，非终身判决 |

### 1.4 作用域

- 默认 Agent 个人分
- 同时滚动到组织级（部门/项目组有集体声誉，影响整组资源与存废）
- 写进 public profile，供路由/招募可见

### 1.5 与红线的关系

- 红线全部为**软红线**，写进公司规章
- Agent 自主遵守
- 违反 → 扣声誉分
- **不设硬闸拦截**（靠规章共识 + 声誉自治）

## 2. 失败协议

### 2.1 两类重试

| 类型 | 说明 | 上限 |
|------|------|------|
| **方案尝试（approach）** | 根本不同的策略 | 每级最多 2 种 |
| **修复迭代（fix）** | 同一方案下对着 reviewer 的具体 findings 修 | 按修复预算/收敛判定 |

### 2.2 Review 标准挂任务评级

| 任务评级 | Review 标准 |
|----------|-------------|
| 公司级 | 强模型 + 跨厂商 + 仿真 |
| 项目级 | 中等标准 |
| 个人级 | 轻量审 |

**不给所有东西上最高门**（成本与重试耗尽都炸在这）。

### 2.3 Review 必须给可执行 findings

- 「拒绝：这 3 条 + 怎么验」
- 否则白耗重试
- 配合 shift-left 自检大降拒绝率

### 2.4 升级 = 泄压，非失败

- 两方案都不过 → 带两份结果 + findings 上报上级
- 上级可：接受有已知局限的版本 / 放宽标准 / 补缺失上下文 / 换更强的人
- 只有一路冒到董事会仍解不了才算失败项目，附全链路报告供复盘
- 董事会只见冒到顶的那些，不会被淹

### 2.5 两级反思

- **per-Agent 任务反思**：深度态结束后写入私有 memory
- **董事会对失败项目的复盘**：组织级

## 3. 决策规则

### 3.1 DRI（直接责任人）

- 每个决策域有**一个**问责人
- 听完输入后拍板——**不投票表决**
- 层级提供责任人：圆桌=CEO，部门内=负责人，准入=该级 reviewer

### 3.2 投票仅作咨询

- 不绑定结果
- 高声誉意见权重更高（声誉加权）
- 责任人仍决定

### 3.3 辩论有界

- 限轮数
- 到点责任人拍板（防无限争论烧 token）

### 3.4 决定 + 异议进 minutes

- 供审计/学习

### 3.5 跨级申诉有界

- 下级可上诉一级
- 到顶即终局
- 允许真实 pushback，防抗命死循环

## 4. 可观测与审计

### 4.1 涌现系统的主控制面

涌现式（无静态 DAG、组织自主生长）意味着同一请求两次跑出的树不同。**不追求复现，靠记录治理**——轨迹即这次的「源代码」。

### 4.2 审计事件

每次跨 Agent 的访问、消息、准入、升级都是审计事件，带 RootNeedID 贯穿。

### 4.3 全链路报告

- 失败项目的完整流转日志 + 各级方案
- 供董事会复盘

### 4.4 Token 消耗治理

| 维度 | 说明 |
|------|------|
| **全链路 token 统计** | 一个需求从圆桌讨论 → 各级流转 → 执行层 → 结果回董事会，整条链路的 token 消耗可见 |
| **各层级看板 token 统计** | 各级看板显示各项目的 token 消耗 |
| **治理 = 观测 + 及时 block** | 刻意不设复杂预算配额；失控时人工 block 项目即止损 |
