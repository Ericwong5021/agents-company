# 治理、审批、Gate 与审计

> 状态：当前
> 上位文档：[产品宪法](PRODUCT-CONSTITUTION.md)

## 1. 治理目标

治理不是让用户批准一切，而是让自治在明确边界内发生：

- 可验收的工作自动向前推进；
- 重大变化在正确层级被发现；
- 权限、风险和受管资源状态不可静默越界；
- 每个正式决定有责任人和证据；
- 用户可以调整信任程度，不需要重新设计工作流。

## 2. 三层规则

| 层级 | 示例 | 可否被 Agent 修改 |
|---|---|---|
| 宪法硬边界 | 私域隔离、用户授权、审计完整性、Worktree 安全 | 不可 |
| 公司政策 | 默认批准等级、预算、招聘与发布规范 | 仅通过治理流程 |
| 项目策略 | 项目风险阈值、模型、测试、单次授权 | 在公司政策允许范围内 |

“组织可以成长”只适用于后两层，不能把所有安全规则降级为软约定。

## 3. Charter Definition of Ready

董事会只有在以下检查通过后才能立项：

| 检查 | 通过条件 |
|---|---|
| Value | 目标用户和价值清楚 |
| Deliverables | 交付物具体且可定位 |
| Acceptance | 每个必须项有可执行验证方式 |
| Scope | 范围与非目标明确 |
| Resources | 所需文件、应用、数据、网页或仓库已声明作用域和处置方式；软件交付单元优先绑定一个主仓库 |
| Ownership | 有唯一项目 DRI |
| Constraints | 权限、预算、时间和技术约束已知 |
| Risk | 主要风险有处理或升级策略 |
| Decisions | 重大待决策项已交给用户或被明确接受为假设 |

未通过时，董事会继续澄清或拆分，不能把“先做做看”伪装成正式执行。探索本身可以是一个有来源、制品和验收的 Discovery 项目。

## 4. 批准等级

### 4.1 预设

| 预设 | 自动执行 | 默认请求用户 |
|---|---|---|
| 自主 | 大部分内部工作和低风险合并 | 高风险、权限升级、宪法边界 |
| 平衡（默认） | 分解、委派、实现、测试、Agent Review | 重大范围变化、外部副作用、最终合并/发布 |
| 严格 | 只读分析和明确授权的低风险动作 | Charter、写入、外部操作、合并等更多节点 |

每个预设必须映射为可检查的规则，而不是只改变 Prompt 语气。

### 4.2 继承

```text
Company Policy
  └─ Project Override
       └─ One-off Authorization
```

下级策略可以更严格。只有用户可以在可允许范围内降低严格度；Agent 只能主动升级。

### 4.3 单次审批选择

- 仅批准本次；
- 批准本项目相同动作类型；
- 更新公司默认规则；
- 拒绝并说明原因；
- 修改条件后批准。

授权必须记录动作类型、资源范围、到期条件和撤销方式，不能用一句“以后都可以”产生无限权限。

## 5. 重大变化判定

至少以下变化必须触发重新评估，是否请求用户由批准等级决定：

- 用户价值或主要交付物变化；
- 必须验收项被删除、降低或替换；
- 项目新增受管资源、扩大写入范围，或软件工作从一个交付单元扩展到另一个仓库；
- 新增外部系统写入、发布、付费或公开通信；
- 预算、时间或数据风险越过阈值；
- 更换 DRI 或大规模改变团队；
- 需要绕开 Worktree、测试或 Review；
- 接受已知高严重度缺陷。

内部实现细节调整、等价重构和不改变验收的任务重排通常不属于重大变化。

## 6. Gate

Gate 是阶段准入，不等同于用户审批。

| Gate | 决策主体 | 证据 |
|---|---|---|
| Charter Ready | 董事会 / Product DRI | Definition of Ready |
| Execution Ready | 项目负责人 | 可执行 Work Items、能力包、权限、资源与验证器 |
| Domain Review | 审查 Agent | 制品、领域验证、findings、验收映射 |
| Delivery Approval | 策略或用户 | 审查通过、外部副作用、风险与授权 |
| Post-delivery Verification | 自动化 + 项目负责人 | 回读、来源、外部结果或领域验收 |
| Release Approval | 策略或用户 | 发布影响、回滚和通知 |

Gate 失败必须给出可操作反馈和回流状态，不能只返回“拒绝”。

软件研发适配器在上述通用 Gate 之外，将 Domain Review 映射为 Agent Review，将 Delivery Approval 映射为 Merge Approval，并增加 Main Verification。

## 7. 软件交付的 Worktree 治理

Worktree 默认开启。开启后以下是硬约束：

- 创建时绑定项目、Work Item、分支、负责人和基础提交；
- 执行、测试、Review、批准、合并、主分支验证有独立状态；
- 合并冲突或审批后新增变更需要重新审查；
- 未验证主分支前不得销毁；
- 失败、取消、异常退出时保留现场；
- 重启扫描孤儿 Worktree，恢复或请求处置；
- 所有销毁都记录合并提交或明确的放弃决定。

关闭 Worktree 时，项目自动启用单写者锁和更严格的写入冲突提示。

## 8. 审计

审计事件至少包含：

- 事件类型、时间和不可变 ID；
- 发起者、代理者和受影响主体；
- Company / Project / Thread / Root Need 关联；
- 请求动作、授权依据和结果；
- 风险级别、资源范围和必要证据引用；
- 若失败，尝试序号、拒绝原因、已尝试方案、下一次调整和恢复建议。

审计只记录私人空间访问的元数据，绝不复制私人内容。高信号会话是用户界面，审计日志是治理证据，两者不能互相替代。

## 9. 声誉与信任

声誉用于辅助选人和监督强度，来源包括：

- 验收通过率与返工；
- 任务难度；
- 交付速度和成本；
- 红线或权限违规；
- 审查质量；
- 近期趋势与合作稳定性。

声誉不能决定私人空间权限，也不能直接修改 Agent 人格。低声誉应带来更小任务或更多审查，而不是人格惩罚。

## 10. 紧急控制

用户始终可以：

- 暂停项目或整个 Control Plane 的新动作；
- 停止指定 Thread；
- 撤销项目或公司授权；
- 保留现场并导出审计；
- 在确认后放弃 Worktree；
- 将批准等级临时提升为严格。

紧急停止必须优先保证状态可恢复，不以强制删除工作区作为默认实现。
